RHCSA EX200 Multi-Server Labs (Revised)

Practice labs for a three-VM RHEL 10 / Rocky Linux 10 setup. Make each change, verify it, then reboot and verify again.

Start with the cheat sheet. Every command from these 25 labs, regrouped by exam objective — searchable and printable. Open cheat sheet →

Servers: server1 = 192.168.1.103 (server1.lab.example.com) | server2 = 192.168.1.104 (server2.lab.example.com) | utility = 192.168.1.105 (utility.lab.example.com)

utility is pre-built, like the exam's classroom server. It provides the package repo, NFS exports, an NTP server, and a Flatpak remote. You only configure server1 and server2 to use it; you never do lab tasks on utility.

See the lab diagram.What runs on each node, which disks to use, ports, and what to have ready before Lab 1.Open lab diagram →

Commands are written for a regular user with sudo rights (a member of wheel). Anything that needs root starts with sudo. Files are written with sudo tee, because sudo echo ... > file fails: the > is handled by your own shell, not by sudo. On the exam you can work this way, or open a root shell once with sudo -i and leave the sudo off.

How to use this workbook

  • Do every lab in the same order: make the change, verify it, then reboot and verify again. The exam is graded after a reboot, so anything that doesn't survive one scores zero.
  • Before any reboot that follows an /etc/fstab change, run findmnt --verify. A bad fstab line can drop the server into emergency mode.
  • Never "fix" SELinux by setting it to permissive or disabled. Read the denial, then fix the label, port, or boolean.
  • When you forget syntax, use man <cmd>, man 5 <file>, the EXAMPLES section of man semanage-fcontext, and /usr/share/doc/. They're all available on the exam.
  • Take a VM snapshot of both servers after Lab 1, and again before Lab 3.

Quick standards applied

  • Passwords are set non-interactively with chpasswd.
  • Users are created in the same order on both servers so UIDs match (required for NFS).
  • Custom Apache ports use SELinux type http_port_t; custom web roots use httpd_sys_content_t.
  • NFS shares come from utility. Autofs timeout is 30 seconds, configured with a drop-in in /etc/auto.master.d/.
  • /etc/fstab entries use UUIDs for block devices and _netdev for network mounts.
  • Root password reset uses init=/bin/bash (rd.break no longer works).
  • Container lab removed; Lab 22 covers Flatpak install and removal.

Lab 1: Network Configuration

server1 and server2

Goalstatic IPv4, hostname, and DNS on server1 and server2, so every lab name resolves through utility's DNS, all persistent across reboots.

Steps

# Find the connection name. On RHEL VMs it is often the device name
# (ens160, enp1s0, eth0), not "Wired connection 1".
nmcli con show
nmcli -t -f NAME,DEVICE con show --active
CON="eth0"            # your Hyper-V VMs use eth0; check the nmcli output above

# server1
sudo hostnamectl set-hostname server1.lab.example.com
sudo nmcli con mod "$CON" ipv4.addresses 192.168.1.103/24 ipv4.gateway 192.168.1.1 \
  ipv4.dns 192.168.1.105 ipv4.dns-search lab.example.com ipv4.method manual connection.autoconnect yes
sudo nmcli con up "$CON"

# server2
sudo hostnamectl set-hostname server2.lab.example.com
sudo nmcli con mod "$CON" ipv4.addresses 192.168.1.104/24 ipv4.gateway 192.168.1.1 \
  ipv4.dns 192.168.1.105 ipv4.dns-search lab.example.com ipv4.method manual connection.autoconnect yes
sudo nmcli con up "$CON"

Verify

ip -4 addr show
nmcli -g ipv4.method,ipv4.addresses,ipv4.gateway,ipv4.dns con show "$CON"
hostnamectl
cat /etc/resolv.conf         # nameserver 192.168.1.105, search lab.example.com
getent hosts utility         # 192.168.1.105 utility.lab.example.com (via DNS, not /etc/hosts)
getent hosts server2.lab.example.com
ping -c 2 server2          # from server1
ping -c 2 server1          # from server2
ping -c 2 utility          # from both
sudo reboot                # then repeat the checks

Notes & gotchas

Warning: If you're connected over SSH, nmcli con up drops your session when the address changes. Run it from the VM console.

  • Set ipv4.addresses in the same command as (or before) ipv4.method manual. Manual mode with no address is rejected.
  • RHEL 9 and 10 store connections as keyfiles in /etc/NetworkManager/system-connections/. Old ifcfg files are deprecated in RHEL 9 and not used in RHEL 10, so use nmcli or nmtui.
  • Names resolve through utility's DNS only; there are no /etc/hosts entries, just like the exam. ipv4.dns-search lab.example.com is what makes short names like utility work.
  • If a name doesn't resolve, check cat /etc/resolv.conf first. A typo in the ipv4.dns address shows up here, which is exactly the mistake the exam would catch.
  • utility forwards everything outside lab.example.com upstream, so internet names still work with it as the only DNS server. dig and host need the bind-utils package.
  • Renaming the VMs (from hv-rocky-linux-6 / -7 to server1 / server2) changes how monitoring agents such as node_exporter and alloy identify them, so they'll likely show up as new machines in your dashboards, with the old history under the old names. Nothing breaks; skip the hostnamectl lines if you'd rather keep the dashboards continuous. The lab names resolve through utility's DNS either way.
  • Exam variant: add a static IPv6 address with ipv6.addresses fd00::103/64 ipv6.method manual.

Lab 2: DNF Repository from utility

server1 and server2, using utility

Goalpoint server1 and server2 at the BaseOS and AppStream repos on utility, the way the exam gives you a classroom repo.

Steps — server1 and server2

sudo tee /etc/yum.repos.d/utility.repo <<'EOF'
[BaseOS]
name=RHEL 10 BaseOS (utility)
baseurl=http://utility.lab.example.com/rhel10/BaseOS
enabled=1
gpgcheck=0

[AppStream]
name=RHEL 10 AppStream (utility)
baseurl=http://utility.lab.example.com/rhel10/AppStream
enabled=1
gpgcheck=0
EOF

Steps — exam conditions: only utility's repos

Your Rocky VMs also have their own internet repos (baseos, appstream, extras, epel). While they're on, dnf freely picks them over utility, so later labs would quietly install from the internet. Turn them off so every install comes from utility, as on the exam:

sudo dnf config-manager --set-disabled baseos appstream extras epel
sudo dnf clean all
sudo dnf repolist                    # only BaseOS and AppStream (utility)

Verify

curl -sI http://utility.lab.example.com/rhel10/BaseOS/repodata/repomd.xml | head -1   # HTTP/1.1 200 OK
sudo dnf repolist -v | grep -E 'Repo-id|Repo-pkgs'
sudo dnf --repo BaseOS --repo AppStream list --available | head -3   # packages served by utility
sudo dnf info --available nginx | grep -i ^Repo                    # Repository : AppStream (utility's)

Notes & gotchas

  • utility uses gpgcheck=0, matching its own drop-in at http://utility.lab.example.com/rhel10.repo. If a task says to verify signatures, use gpgcheck=1 plus a gpgkey= line, or run sudo rpm --import on the key the task gives you.
  • Exam shortcut: sudo dnf config-manager --add-repo http://utility.lab.example.com/rhel10/BaseOS (and again for AppStream) writes the repo file for you, but with no gpgcheck= or gpgkey= line. Check the file before relying on it.
  • $releasever and $basearch are dnf variables. In a shell command such as mkdir or curl they expand to empty strings, so don't put them in URLs you test by hand.
  • A failing repo (like a 401 from an expired credential) stops every dnf command. Skip it with --disablerepo=<id> or disable it permanently with sudo dnf config-manager --set-disabled <id>. Plain --disable only sticks with --save.
  • Back to normal (internet updates) when you're done with the labs: sudo dnf config-manager --set-enabled baseos appstream extras epel. While they're off, the VMs only get packages as current as utility's mirror.
  • Repo IDs are case-sensitive: utility's BaseOS and Rocky's baseos are separate repos.
  • Don't verify with dnf info on an installed package such as nfs-utils: it reports the repo it was originally installed from, not utility.

Lab 3: Apache: move DocumentRoot + TCP/82 under SELinux & firewalld

server1

Goalserve /webdata on port 82 with SELinux enforcing, verify from server2, and survive a reboot.

Flowbaseline → move DocumentRoot → SELinux file-context denial → fix → port 82 → SELinux port denial → fix → "forget" the firewall → firewall denial → fix → reboot test → cleanup.

0. Prep

sudo dnf -y install httpd policycoreutils-python-utils setroubleshoot-server
sudo systemctl enable --now httpd
systemctl is-enabled firewalld auditd       # both should already be enabled
  • policycoreutils (base, preinstalled): restorecon, getenforce, setenforce
  • policycoreutils-python-utils: semanage, audit2why, audit2allow
  • setroubleshoot-server: sealert and plain-English AVC summaries in the journal
  • auditd: writes AVC denials to /var/log/audit/audit.log. Never run systemctl restart auditd (the unit refuses it); use sudo service auditd restart.

1. SELinux awareness

getenforce
sestatus
grep ^SELINUX= /etc/selinux/config

Three ways to view denials (used throughout):

sudo ausearch -m avc -ts recent -i          # raw events; "recent" = last 10 minutes
sudo sealert -a /var/log/audit/audit.log    # analysis plus a suggested fix
sudo journalctl -t setroubleshoot --since "-10min"   # empty? wait a few seconds and rerun

2. Baseline on port 80

echo "Hello from original DocumentRoot" | sudo tee /var/www/html/index.html
sudo firewall-cmd --permanent --add-service=http  # server1 only allows ssh and cockpit by default
sudo firewall-cmd --reload
curl http://localhost                         # on server1
curl http://192.168.1.103                      # on server2

Optional: move the welcome page aside so a 403 shows as a 403 instead of the distro's test page.

sudo mv /etc/httpd/conf.d/welcome.conf /root/welcome.conf.bak

3. Move DocumentRoot to /webdata (file-context denial)

sudo mkdir /webdata
echo "Hello from /webdata" | sudo tee /webdata/index.html
ls -Zd /var/www/html /webdata        # httpd_sys_content_t vs default_t

Edit the config with sudo vi /etc/httpd/conf/httpd.conf. CHANGE the existing DocumentRoot line (don't add a second one) and add a Directory block:

DocumentRoot "/webdata"
<Directory "/webdata">
    AllowOverride None
    Require all granted
</Directory>
sudo apachectl configtest             # expect "Syntax OK"
sudo systemctl restart httpd
curl -i http://localhost              # expect HTTP/1.1 403 Forbidden

Read the denial. Look for denied { getattr } ... tcontext=...default_t ... comm="httpd" (some systems log { read } instead; either means httpd can't use a default_t file):

sudo ausearch -m avc -ts recent -i
sudo ausearch -m avc -ts recent | sudo audit2why  # SELinux explains the cause
sudo journalctl -t setroubleshoot --since "-10min"   # empty? wait a few seconds and rerun

Fix it (a persistent rule, then apply it):

sudo semanage fcontext -a -t httpd_sys_content_t "/webdata(/.*)?"
sudo restorecon -Rv /webdata
ls -Z /webdata/index.html             # now httpd_sys_content_t
curl http://localhost                 # "Hello from /webdata"
  • Alternative fix: copy the rules for /var/www with sudo semanage fcontext -a -e /var/www /webdata.
  • Trap: chcon works until the next relabel, then it's gone. Use semanage fcontext plus restorecon for a persistent fix.
  • Bonus gotcha: create a file in your home directory and mv it into /webdata. It keeps user_home_t, because mv preserves context while cp inherits the target's. Check with ls -Z, then fix it with restorecon.

4. Change to port 82 (port-type denial)

Run sudo vi /etc/httpd/conf/httpd.conf and change Listen 80 to Listen 82.

sudo apachectl configtest
sudo systemctl restart httpd          # FAILS (this is expected)
systemctl status httpd --no-pager     # "could not bind to address ... :82"
sudo ausearch -m avc -ts recent -i    # denied { name_bind } ... src=82

Port 82 isn't in the default http_port_t list (80, 81, 443, 488, 8008, 8009, 8443, 9000). Fix:

sudo semanage port -l | grep -w http_port_t
sudo semanage port -a -t http_port_t -p tcp 82
sudo systemctl restart httpd
sudo ss -tlnp | grep :82
curl http://localhost:82              # works locally (loopback isn't firewalled)

5. "Forget" the firewall (firewall denial)

sudo firewall-cmd --set-log-denied=all
sudo firewall-cmd --get-log-denied

On server2:

curl -m 5 http://192.168.1.103:82      # fails: "Could not connect to server" (older curl: "No route to host")

On server1:

sudo journalctl -k --since "-5min" | grep "DPT=82" | tail
sudo journalctl -k -f | grep --line-buffered "DPT=82"  # live view; Ctrl+C to stop

Note: Testing from localhost will NOT show a denial, because firewalld doesn't filter the loopback interface.

Fix:

sudo firewall-cmd --permanent --add-port=82/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

On server2, curl http://192.168.1.103:82 should return "Hello from /webdata". You don't need to restart httpd for firewall changes.

6. Persistence check (the exam grades after reboot)

sudo semanage fcontext -l -C          # your custom file-context rule
sudo semanage port -l -C              # your custom port rule
systemctl is-enabled httpd
sudo reboot
# after reboot, from server2:
curl http://192.168.1.103:82
# on server1:
sudo ausearch -m avc -ts boot         # expect <no matches>

7. Cleanup

sudo firewall-cmd --set-log-denied=off
sudo mv /root/welcome.conf.bak /etc/httpd/conf.d/welcome.conf  # if you moved it

Optional extra: run sudo setenforce 0, repeat the /webdata test with the wrong label, and note that the denial is logged but not enforced. Then run sudo setenforce 1. This is why permissive mode is a diagnostic tool, not a fix.

Lab 4: Users & Groups

both servers

Goalgroup admin; users harry and natasha with admin as a supplementary group; sarah with no interactive shell.

Steps

sudo groupadd admin
sudo useradd -G admin harry
sudo useradd -G admin natasha
sudo useradd -s /sbin/nologin sarah
printf '%s\n' 'harry:Harry123' 'natasha:Natasha123' 'sarah:Sarah123' | sudo chpasswd

Verify

id harry; id natasha; id sarah
getent group admin
getent passwd sarah | cut -d: -f7     # /sbin/nologin
sudo su - sarah                       # "This account is currently not available."

Notes & gotchas

  • Run the commands in the same order on both servers so the UIDs match. NFS (Lab 6) maps ownership by number, not name.
  • Do this lab before Labs 6 and 11. They create high-numbered users (remoteuser1 = 5000 on server2, billy = 6969 on both), and after that useradd numbers new users above the highest one, so redoing Lab 4 later gives harry 5001 on server2 but 6970 on server1. If you must redo it, set the numbers explicitly: sudo useradd -u 1002 -G admin harry, and so on.
  • sudo usermod -G admin user replaces all supplementary groups. Use sudo usermod -aG admin user to append.
  • natasha was used by Labs 7, 8, and 13 but never created in the original workbook; she is created here.

Lab 5: Collaboration Directory with SGID

both servers

Goal/srv/common_admin owned by group admin; new files inherit the group; no access for anyone else.

Steps

sudo mkdir -p /srv/common_admin
sudo chgrp admin /srv/common_admin
sudo chmod 2770 /srv/common_admin

Verify

ls -ld /srv/common_admin                                  # drwxrws---. root admin
sudo su - harry   -c 'touch /srv/common_admin/harry.txt'
sudo su - natasha -c 'touch /srv/common_admin/natasha.txt'
sudo ls -l /srv/common_admin                              # both files: group admin
sudo su -s /bin/bash sarah -c 'ls /srv/common_admin'     # Permission denied

Notes & gotchas

  • Extension: sudo chmod 3770 /srv/common_admin adds the sticky bit, so members can't delete each other's files. Test it with sudo su - natasha -c 'rm -f /srv/common_admin/harry.txt', which should fail with "Operation not permitted". Without -f, rm first asks "remove write-protected regular empty file?" because harry's file is read-only for natasha; answering y gives the same denial.
  • Extension: sudo setfacl -m d:g:admin:rwx /srv/common_admin adds a default ACL so new files are group-writable regardless of the creator's umask.

Lab 6: NFS Client: Static Mounts & autofs

server2, using utility

Goalon server2, mount utility's NFS shares persistently (data read-write, docs read-only) and automount the remote home directories under /home/guests with a 30-second timeout.

utility exports: /exports/data (rw), /exports/docs (ro), /home/guests (rw).

Part A: static mounts

sudo dnf -y install nfs-utils autofs
showmount -e utility.lab.example.com
sudo mkdir -p /mnt/data /mnt/docs
sudo tee -a /etc/fstab <<'EOF'
utility.lab.example.com:/exports/data  /mnt/data  nfs  defaults,_netdev,rw  0 0
utility.lab.example.com:/exports/docs  /mnt/docs  nfs  defaults,_netdev,ro  0 0
EOF
sudo systemctl daemon-reload
sudo mount -a
findmnt -t nfs4
cat /mnt/docs/policy.txt
echo test | sudo tee /mnt/data/from-server2.txt
ls -l /mnt/data                    # owner nobody: root is squashed on this export
sudo touch /mnt/docs/x            # "Read-only file system" (expected)

Part B: autofs for remote home directories

# remoteuser1 is UID 5000 on utility; create the same user here, home on NFS (-M: don't create it)
sudo useradd -u 5000 -M -d /home/guests/remoteuser1 remoteuser1
echo 'remoteuser1:Remote123' | sudo chpasswd

echo '/home/guests  /etc/auto.guests  --timeout=30' | sudo tee /etc/auto.master.d/guests.autofs
echo '*  -fstype=nfs,rw  utility.lab.example.com:/home/guests/&' | sudo tee /etc/auto.guests
sudo systemctl enable autofs
sudo systemctl restart autofs     # restart, so map changes are read

Verify

ls /home/guests                    # empty: normal, keys appear on access
sudo su - remoteuser1 -c 'pwd; touch ~/from-server2; ls -l'   # logging in triggers the mount
mount | grep /home/guests          # mounted now
mount | grep '/home/guests type autofs'   # shows timeout=30: the idle timeout is set
sudo reboot                        # then findmnt -t nfs4 and the autofs test again

Notes & gotchas

  • In /etc/auto.guests, * matches any directory name and & is replaced by it, so /home/guests/alice mounts utility:/home/guests/alice.
  • The UID must match utility's (5000). With a different UID, remoteuser1 can't read its own home, which is mode 700.
  • For SSH logins into an NFS home, SELinux also needs sudo setsebool -P use_nfs_home_dirs on. su - works without it.
  • sudo systemctl enable --now autofs doesn't reload maps if autofs was already running. Restart it after editing maps.
  • The idle unmount may never happen on these VMs. In testing, autofs tried to expire the mount every 8 seconds and the kernel always reported it busy, even though nothing used it and a manual sudo umount worked. System services that run in private mount namespaces (NetworkManager, rsyslog, systemd-userdbd and others) each hold a copy of the mount, which keeps autofs from expiring it. Your configuration is fine; check that timeout=30 shows on the autofs mount instead of waiting for the unmount.
  • Never userdel -r remoteuser1 to clean up. utility's /home/guests export doesn't squash root, so -r deletes remoteuser1's real home on utility. Use sudo userdel remoteuser1 without -r.
  • _netdev makes the boot wait for the network before mounting the static shares.
  • chown/chmod on a client mount point does nothing useful; the share's own permissions apply.

Lab 7: Scheduling with cron and at

server1 (cron) and server2 (deny)

Goalharry runs a logging job every 5 minutes on server1; natasha is denied cron on server2.

Steps — server1

sudo tee /usr/local/bin/ex200.sh <<'EOF'
#!/bin/bash
echo "EX200 message $(date)" >> /var/log/ex200.log
EOF
sudo chmod 755 /usr/local/bin/ex200.sh

# harry can't write to root-owned /var/log, so pre-create the log for him
sudo touch /var/log/ex200.log
sudo chown harry:harry /var/log/ex200.log

# Append to harry's crontab without opening an editor
(sudo crontab -u harry -l 2>/dev/null; echo '*/5 * * * * /usr/local/bin/ex200.sh') | sudo crontab -u harry -

Steps — server2

echo natasha | sudo tee -a /etc/cron.deny

Verify

# server1
systemctl is-active crond
sudo crontab -u harry -l
# wait 5+ minutes
tail -n 5 /var/log/ex200.log
sudo grep CROND /var/log/cron | tail -n 3

# server2
sudo su - natasha -c 'crontab -l'  # "You (natasha) are not allowed to use this program"

Notes & gotchas

  • In the original, harry's job could never write to /var/log/ex200.log, so the job failed silently every 5 minutes.
  • Test the deny with crontab -l, not crontab -e. If the deny isn't working, -e opens an editor and hangs the test.
  • If /etc/cron.allow exists, only users listed there may use cron, and cron.deny is ignored.
  • Common exam variant: */2 * * * * logger "EX200 in progress", verified with sudo journalctl -t harry.
  • One-off jobs with at (needs sudo dnf -y install at; sudo systemctl enable --now atd):
echo 'date > /tmp/at-test.txt' | at now + 2 minutes
atq

Lab 8: File ACLs

server1

Goal/var/tmp/fstab owned by root, readable by others; harry can read and write; natasha has no access at all.

Steps

sudo cp /etc/fstab /var/tmp/fstab
sudo chown root:root /var/tmp/fstab
sudo chmod 644 /var/tmp/fstab
sudo setfacl -m u:harry:rw- /var/tmp/fstab
sudo setfacl -m u:natasha:--- /var/tmp/fstab
getfacl /var/tmp/fstab

Verify

ls -l /var/tmp/fstab                                     # -rw-rw-r--+ (the "+" means ACLs; see notes)
sudo su - harry   -c 'echo "# harry was here" >> /var/tmp/fstab' && echo "harry write OK"
sudo su - natasha -c 'cat /var/tmp/fstab'                 # Permission denied
sudo su -s /bin/bash sarah -c 'wc -l /var/tmp/fstab'    # prints a line count: readable via "other"

Notes & gotchas

  • The original used mode 640, which already locked natasha out through "other", so the natasha ACL proved nothing. With 644, the ACL entry is the only thing denying her.
  • /var/tmp survives reboots, while /tmp is cleaned periodically, so use /var/tmp for anything that must still be there for grading.
  • ls -l shows -rw-rw-r--+, not the 644 you set. With ACLs, the middle three letters show the ACL mask (the most any named user or group can get), which harry's rw- raised. The owning group itself still has r--; getfacl shows the real entries.
  • chmod g-w on a file with ACLs changes the ACL mask, which can silently remove harry's write. Check getfacl for "#effective:".
  • Remove entries with sudo setfacl -x u:natasha /var/tmp/fstab, or all ACLs with sudo setfacl -b.
  • The optional NFS export of /tmp was dropped. Exporting /tmp is poor practice, and the cross-host test depended on matching UIDs and NFSv4 ACL mapping.

Lab 9: Time Sync with chrony

server1 and server2, using utility

Goalserver1 and server2 sync time only from utility.

Steps — server1 and server2

sudo dnf -y install chrony
sudo sed -ri 's/^(pool|server) /#&/' /etc/chrony.conf     # comment out the default pool line
echo 'server utility.lab.example.com iburst' | sudo tee -a /etc/chrony.conf
sudo systemctl enable chronyd
sudo systemctl restart chronyd
sudo timedatectl set-ntp true

Verify

chronyc sources -v        # "^* utility.lab.example.com" (* = selected source)
chronyc tracking
timedatectl               # "System clock synchronized: yes", "NTP service: active"

Notes & gotchas

  • RHEL's default file uses a pool line, not server. A sed that only matches ^server leaves the public pool active alongside utility.
  • chronyd is already running on a default install, so systemctl enable --now doesn't reload the edited config. Always restart after editing /etc/chrony.conf.
  • ^? in chronyc sources means the server isn't reachable yet. Check the name resolves and wait a minute after restarting.

Lab 10: Find & Copy Large Files

server1

Goalfind every file larger than 4 MiB and copy it into /root/find_large_files.

Lab 12: Archive & Compress

server1

Goalcreate a bzip2-compressed archive /root/backup.tar.bz2 containing /usr/local, then restore it to a separate directory and to its original location.

Create

sudo tar -cjf /root/backup.tar.bz2 /usr/local

Verify

sudo file /root/backup.tar.bz2         # bzip2 compressed data
sudo tar -tjf /root/backup.tar.bz2 | head  # names start with usr/local/, no leading /

Extract to a separate directory

Safe: nothing on the system is overwritten. Use this to inspect a backup or pull out one file.

sudo mkdir -p /root/restore
sudo tar -xjf /root/backup.tar.bz2 -C /root/restore
sudo ls -l /root/restore/usr/local
sudo diff -r /usr/local /root/restore/usr/local  # no output = identical contents

# Just one directory or file: name it as the listing shows it
sudo tar -xjf /root/backup.tar.bz2 -C /root/restore usr/local/bin

Extract to the original location

The names in the archive are relative (usr/local/...), so extracting from / puts them back at /usr/local.

Warning: this overwrites the current files in /usr/local with the archived versions. Files created since the backup are left alone, not deleted.

sudo tar -xjf /root/backup.tar.bz2 -C /
sudo restorecon -Rv /usr/local          # fix SELinux labels on restored files

Notes & gotchas

  • Without -C, tar extracts into the current directory. -C must point at a directory that already exists.
  • Permissions and ownership: run with sudo (as root), tar restores each file's owner, group, mode, and timestamps automatically. Without sudo, extracted files are owned by you and your umask applies; add -p to keep the archived modes.
  • SELinux contexts and ACLs are not saved by default. Either run sudo restorecon -R after restoring to the original location, or add --selinux --acls both when creating and when extracting.
  • "Removing leading `/' from member names" is a normal message. It is why extraction lands under the -C directory instead of overwriting the original paths.
  • Mnemonic: z = gzip (.gz), j = bzip2 (.bz2), J = xz (.xz). Use the one the task asks for. When extracting, current tar detects the compression, so tar -xf also works.
  • If -j fails, install bzip2: sudo dnf -y install bzip2.

Lab 18: LVM: VG datastore, LV database, mounted by UUID

server1

GoalVG datastore with 8 MiB extents; LV database of 500 MiB with XFS, mounted persistently at /mnt/database.

Warning: The original built the VG on loop devices. Loop devices don't come back after a reboot, so the fstab entry fails and the server boots into emergency mode. Add a real empty virtual disk (2 GiB or more) instead. On server1 that's the disk in Hyper-V SCSI slot LUN 3; see the lab diagram.

Pick disks by slot, not by sdX name. The kernel names disks in the order it detects them at boot, which doesn't follow the Hyper-V slots: on server1 the OS disk (LUN 0) is currently sdb, and after a reboot it could be sda. /dev/disk/by-path/ names are tied to the slot, so the steps below use those.

Redoing this lab? Clean up first. A leftover /mnt/database line in fstab points at a filesystem that no longer exists and sends the next boot into emergency mode.

sudo swapoff /dev/datastore/swap     # only if you did the swap lab
sudo umount /mnt/database
sudo wipefs -a /dev/datastore/database   # erase the XFS marker, or the next lvcreate asks "Wipe it? [y/n]"
sudo wipefs -a /dev/datastore/swap       # only if you did the swap lab
sudo vgremove -y datastore
sudo vi /etc/fstab                   # delete the /mnt/database and datastore swap lines
sudo systemctl daemon-reload

Steps — partition the new disk

ls -l /dev/disk/by-path/                 # Hyper-V slot (LUN) -> today's sdX name; slots never change
DISK=$(readlink -f /dev/disk/by-path/acpi-MSFT1000:00-scsi-0:0:0:3)   # server1 LUN 3: a 5 GiB empty disk
lsblk $DISK                              # must show 5G and NO partitions. Anything else: STOP
P=$DISK                  # partition prefix; for NVMe use P=${DISK}p
sudo wipefs -a $DISK     # ERASES the disk: clears old LVM/XFS signatures if you're redoing the lab
sudo parted -s $DISK mklabel gpt
sudo parted -s $DISK mkpart lvm1 1MiB 1025MiB
sudo parted -s $DISK set 1 lvm on
sudo parted -s $DISK mkpart lvm2 1025MiB 100%
sudo parted -s $DISK set 2 lvm on
sudo udevadm settle
lsblk $DISK              # ${P}1 and ${P}2 (NVMe: nvme1n1p1 / p2)

Steps — LVM, filesystem, mount

sudo pvcreate ${P}1 ${P}2
sudo vgcreate -s 8M datastore ${P}1 ${P}2
sudo lvcreate -L 500M -n database datastore  # rounds up to 504M (63 x 8M extents)
#   by extents instead:  sudo lvcreate -l 60 -n database datastore   (60 x 8M = 480M)
sudo mkfs.xfs /dev/datastore/database
sudo mkdir -p /mnt/database
echo "UUID=$(sudo blkid -s UUID -o value /dev/datastore/database)  /mnt/database  xfs  defaults  0 0" | sudo tee -a /etc/fstab
sudo systemctl daemon-reload
sudo mount -a
sudo chmod 1777 /mnt/database              # AFTER mounting: sets the filesystem's root

Verify

sudo pvs; sudo vgs; sudo lvs
sudo vgdisplay datastore | grep 'PE Size'  # 8.00 MiB
findmnt /mnt/database
df -h /mnt/database                         # about 440M usable: XFS keeps room for its log
sudo findmnt --verify
sudo reboot                                 # then findmnt /mnt/database again

Notes & gotchas

  • lvs shows the volume's size (504M); df shows what the filesystem can use (about 440M), because XFS reserves space for its log and metadata. A task that says "500 MiB logical volume" is checked with lvs.
  • If lvcreate stops with WARNING: xfs signature detected ... Wipe it? [y/n], the disk still holds a filesystem from an earlier attempt. Answer y. If you pasted a block, the next pasted line gets taken as the answer and the create aborts, so run that lvcreate again by itself. lvcreate -y answers yes for you.
  • -L sets a size (500M, 1G); -l sets a count of extents (60) or a percentage (100%FREE).
  • The original ran chmod 1777 before mounting, which changed the empty mount point that the filesystem then hides.
  • If you must use loop devices, add nofail to the fstab options so the boot continues. After each reboot, re-run sudo losetup and sudo vgchange -ay datastore.
  • For ext4, use mkfs.ext4 and type ext4 in fstab. Everything else is the same.

Lab 24: Diagnostics Drill: ss, journalctl, ausearch

server2

Goalanswer "what's listening, what failed, and who changed what" from memory. Do the scenarios first; the solutions follow.

Setup

sudo dnf -y install nginx nmap-ncat
sudo systemctl enable --now nginx
sudo firewall-cmd --permanent --add-service=http; sudo firewall-cmd --reload
sudo useradd -m labuser
echo 'labuser:Labuser123' | sudo chpasswd

Note: Run this drill on server2. On server1, httpd from Lab 3 may hold port 80, and nginx would fail to start.

Part 1 — Scenarios

Scenario 1: what is listening, and who owns it? List listening TCP sockets with process info; confirm what owns port 80.

Scenario 2: who is connected right now? From server1, hold a connection open with exec 3<>/dev/tcp/server2/80; printf 'GET / HTTP/1.1\r\n' >&3. It stays up for about a minute; close it with exec 3>&-. On server2, show established connections to port 80, the remote IPs, and the owning process.

Scenario 3: a service failed. Prove why. Break nginx with sudo mv /etc/nginx/nginx.conf /etc/nginx/nginx.conf.broken and sudo systemctl restart nginx. Show the status, the error explaining the failure, and the last 50 unit log lines.

Scenario 4: what happened since boot? Show all errors since boot, nginx logs since boot, and a 5-minute window that includes your failure.

Scenario 5: who edited a protected file? Watch /etc/hosts with an audit rule, then change it (commands are in the solution). Find the events, the real user behind the change, and the executable used.

Scenario 6: find failed logins. As your normal user (not with sudo, since root's su never asks for a password), run su - labuser and type a wrong password twice. Find the failures in the audit log and the journal.

Scenario 7: detect a suspicious listener. Start ncat -lk 5555 &. Prove it's listening and get its PID, then kill it and confirm it's gone.

Part 2 — Solutions

Scenario 1

sudo ss -ltnp                     # -l listening, -t TCP, -n numeric, -p process
sudo ss -ltnp 'sport = :80'

Scenario 2

sudo ss -tnp state established '( sport = :80 )'
ss -Htn state established '( sport = :80 )' | awk '{print $4}' | sed 's/:[0-9]*$//' | sort -u

Note: With a state filter, ss drops the State column, so the peer address is column 4, not 5 (the original used $5). -H drops the header line. The sed strips only the trailing :port, so it also works when a dual-stack listener shows the peer as [::ffff:192.168.1.103].

  • Why not a curl loop? Each request lasts milliseconds, so ss almost never catches one open.
  • Why send a request line? Some web servers (Apache, for one) don't treat a connection as established until data arrives, so a silent connection shows as SYN-RECV.

Scenario 3

systemctl status nginx --no-pager
sudo journalctl -xeu nginx --no-pager                  # includes nginx's own "[emerg]" line
sudo journalctl -u nginx --since "-10min" -p err --no-pager # only systemd's "Failed to start"
sudo journalctl -u nginx -n 50 --no-pager
# fix
sudo mv /etc/nginx/nginx.conf.broken /etc/nginx/nginx.conf
sudo systemctl restart nginx

Note: nginx writes its error to stderr, which the journal stores at "info" priority. That's why -p err alone hides the actual reason.

Scenario 4

sudo journalctl -b -p err --no-pager
sudo journalctl -b -u nginx --no-pager
sudo journalctl -u nginx --since "-10min" --no-pager                  # relative window
sudo journalctl -u nginx --since "15:00" --until "15:05" --no-pager    # absolute: use the time of YOUR failure

Scenario 5

sudo auditctl -w /etc/hosts -p wa -k hosts_watch
echo "# lab test $(date)" | sudo tee -a /etc/hosts
sudo ausearch -k hosts_watch -i
sudo ausearch -k hosts_watch -i | grep -E -o '(auid|uid|exe|comm)=[^ ]+' | sort -u

auid is the user who originally logged in, and it stays the same through sudo and su. uid is who the process ran as (root). For a rule that survives reboot, put -w /etc/hosts -p wa -k hosts_watch in /etc/audit/rules.d/hosts.rules and run sudo augenrules --load.

Lab 25: Grow the Root Filesystem After Enlarging the VM Disk

server1

Goalthe VM's disk was enlarged in the hypervisor; grow the partition, PV, LV, and filesystem so / uses the new space, without rebooting into rescue mode.

Layer model

Hypervisor disk → partition (growpart) → PV (pvresize) → VG → LV + filesystem (lvextend -r). Every layer has to grow, in that order.

Steps

# 0. Before: note the sizes, then find the disk and partition behind VG rl
lsblk; df -h /; sudo pvs; sudo vgs
ROOTPV=$(sudo pvs --noheadings -o pv_name -S vg_name=rl | tr -d ' ')   # e.g. /dev/sdb3
DISK=$(lsblk -dno pkname $ROOTPV)                                      # e.g. sdb
PART=$(cat /sys/class/block/${ROOTPV#/dev/}/partition)                # e.g. 3
echo $ROOTPV $DISK $PART

# 1. Enlarge the virtual disk in the hypervisor.
#    Hyper-V: delete ALL checkpoints first (including the Lab 1 / Lab 3 ones),
#    then Settings > the disk > Edit > Expand. The VM can stay running.

# 2. Make the kernel see the new disk size (or reboot)
echo 1 | sudo tee /sys/class/block/$DISK/device/rescan   # SCSI disks (Hyper-V, VMware); virtio usually updates by itself
lsblk /dev/$DISK                                         # disk is bigger; the partition is NOT yet

# 3. Grow the partition holding the PV
sudo dnf -y install cloud-utils-growpart
sudo growpart /dev/$DISK $PART
#   alternative: sudo parted /dev/$DISK resizepart $PART 100%
#   (answer Fix to the GPT warning, then Yes), then sudo partprobe

# 4. Grow the PV, then the LV and filesystem together
sudo pvresize $ROOTPV
sudo vgs                                       # VFree > 0 now
sudo lvextend -r -l +100%FREE /dev/rl/root   # Rocky VG is rl; on RHEL it's rhel

Verify

lsblk
df -h /

Common failure modes

SymptomCauseFix
lsblk shows the old disk sizeKernel hasn't rescannedRescan the device or reboot
pvresize reports no changePartition wasn't growngrowpart / parted resizepart first
lvextend: insufficient free extentsPV not resizedpvresize
resize2fs fails with "Bad magic number"Filesystem is XFS, not ext4Use lvextend -r or xfs_growfs /
growpart can't grow the partitionIt isn't the last partition on the diskAdd a new disk instead: pvcreate → vgextend → lvextend -r
Hypervisor won't enlarge the diskSnapshots/checkpoints exist (the workbook has you take some after Lab 1 and before Lab 3)Delete or merge them first

Practice variations

  • Root disk expansion as above: grow a 20 GiB disk to 40 GiB.
  • Add a new disk instead: sudo pvcreate /dev/sdd; sudo vgextend rl /dev/sdd; sudo lvextend -r -l +100%FREE /dev/rl/root (with a new empty disk attached as sdd).

Note: Memory anchor: disk → growpart → pvresize → lvextend -r. The original skipped the partition step and used Ubuntu names and resize2fs. RHEL's default root is XFS on /dev/rhel/root; on your Rocky VMs it's /dev/rl/root. Check the names on your system with lvs. The variables in step 0 find the disk from the VG, so the steps work whatever sdX name the disk has today.
