LiteLLM Gateway Labs: Chat & Agents

Hands-on labs for sending every chat and every AI agent in a home lab through one LiteLLM gateway: one address, one key per app, and one log of who asked what.

You'll start with plain chat requests, put a chat web UI in front of the gateway, then build five agents: a single tool-using agent, agents running as always-on services, agents published through the gateway over A2A, an agent whose tools come from an MCP server, and a coordinator that hands work to the other agents. Lab 10 then points a coding agent at the gateway too.

The hosts

HostRoleWhat runs there
gateway 192.168.1.101The LiteLLM gateway, port 4000LiteLLM and its Postgres database. Assumed to be running already. Lab 0 is the reference for installing or fixing it.
agent host 192.168.1.100Everything you build, and where you type the commandsOpen WebUI (3000), ops-agent (8601), writer-agent (8602), the lab-tools MCP server (8701), and your Python scripts
model server 192.168.1.194Where the model actually runsLM Studio on port 1234 serving qwen/qwen3.8-27b. Any OpenAI-compatible server, or a cloud provider, works the same way.

Nothing talks to the model server directly. The chat UI, the agents and the coding agent all send their requests to the gateway, and the gateway checks the key and forwards the request to the model. That's what lets you swap models, limit an app, or see what an agent did, in one place.

Podman, and keeping things running after a reboot

Every container in these labs runs under rootful Podman (sudo podman); there's no Docker anywhere. A container started with plain podman run stops when the host reboots and stays stopped, because there's no always-running daemon to bring it back, as there is with Docker. There are two ways to fix that:

ApproachHow it worksUse it when
Quadlet (used in every lab)You write a small .container file in /etc/containers/systemd/. Podman turns it into a normal systemd service, so systemctl start, status, restart and journalctl all work, and the [Install] section starts it at boot.Anything that should keep running. This is the Red Hat-recommended way on Podman 4.4 and newer (Rocky 9 and 10 have Podman 5).
podman run --restart=always plus podman-restart.service--restart=always restarts a crashed container. After a reboot, podman-restart.service (if it's enabled) starts every container that has that restart policy.A quick fix for a container someone already started by hand. Lab 1 shows how to check for this and how to convert to a Quadlet.

A Quadlet file has three sections: [Unit] (a description and what it depends on), [Container] (everything you'd otherwise type after podman run: image, ports, volumes, environment), and [Service]/[Install] (systemd's restart policy and "start at boot"). After adding or changing one, run sudo systemctl daemon-reload so systemd regenerates the service. You don't run systemctl enable on Quadlet services; the [Install] section takes care of that.

Before you start

  • SSH with sudo on 192.168.1.100 and 192.168.1.101, both Rocky Linux 9 or 10 with Podman 5.
  • LiteLLM running on .101 with a master key and a database (virtual keys, used from Lab 3 on, need it). Lab 1 checks both; Lab 0 covers whatever is missing.
  • A model that can call tools. These labs use qwen/qwen3.8-27b in LM Studio. In LM Studio, set its default context length to at least 32k (gear icon on the model, then Context Length). LM Studio loads models on demand with that setting, and a small default leaves a "thinking" model no room to answer.
  • The labs were tested with LiteLLM v1.104.0, Podman 5.8, Python 3.12, openai 3.24, mcp 2.3 and a2a-sdk 1.2.

Part 1: Podman

Rocky Linux and RHEL ship Podman in the base repositories. Quadlet, the feature that turns container files into systemd services (see the overview), is built into Podman 4.4 and newer.

sudo dnf -y install podman jq
podman --version                           # 5.x on Rocky 9.6+ and 10
ls /usr/libexec/podman/quadlet             # present = Quadlet is available

Everything here runs as root (sudo podman). Root containers and their Quadlet files live in /etc/containers/systemd/; rootless ones would live in ~/.config/containers/systemd/ and need loginctl enable-linger to start at boot, which is why these labs stick to rootful.

Part 2: A fresh install

The result is two Quadlet services: litellm-db (Postgres, which stores virtual keys, agents and spend logs) and litellm (the gateway), joined by a private network so the database is never exposed on the LAN.

Secrets. Two env files, readable by root only. Podman reads them when it creates each container, so no secret appears in a config file or in ps output. The master key must start with sk-.

sudo mkdir -p /opt/litellm
sudo install -m 600 /dev/null /opt/litellm/litellm.env      # create both files, readable by root only
sudo install -m 600 /dev/null /opt/litellm/db.env
DBPASS=$(openssl rand -hex 24)
read -rsp 'Admin UI password: ' UIPASS; echo

printf '%s\n' "POSTGRES_USER=litellm" "POSTGRES_PASSWORD=$DBPASS" "POSTGRES_DB=litellm" \
  | sudo tee /opt/litellm/db.env >/dev/null

printf '%s\n' \
  "LITELLM_MASTER_KEY=sk-$(openssl rand -hex 24)" \
  "LITELLM_SALT_KEY=sk-$(openssl rand -hex 24)" \
  "DATABASE_URL=postgresql://litellm:$DBPASS@litellm-db:5432/litellm" \
  "UI_USERNAME=admin" "UI_PASSWORD=$UIPASS" \
  "LMSTUDIO_API_BASE=http://192.168.1.194:1234/v1" \
  | sudo tee /opt/litellm/litellm.env >/dev/null
unset DBPASS UIPASS

Config. model_list is the list of models the gateway serves. model_name is the name clients ask for; model is the real model, where the openai/ prefix means "talk to this server with the OpenAI API", which LM Studio speaks. os.environ/NAME tells LiteLLM to read a value from the environment. Add one entry per model you want to serve.

sudo tee /opt/litellm/config.yaml >/dev/null <<'EOF'
model_list:
  - model_name: qwen3.8-27b
    litellm_params:
      model: openai/qwen/qwen3.8-27b       # the model's id in LM Studio
      api_base: os.environ/LMSTUDIO_API_BASE
      api_key: not-needed                  # LM Studio doesn't check keys

litellm_settings:
  drop_params: true          # ignore request options the model server doesn't support
  request_timeout: 600       # local models can be slow on long prompts

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL
EOF

Quadlet files. A network, a volume for the database files, and one .container file per container. Requires= and After= start the database first, and Notify=healthy makes systemd wait until Postgres actually answers before it starts LiteLLM.

sudo tee /etc/containers/systemd/litellm.network >/dev/null <<'EOF'
[Network]
NetworkName=litellm
EOF

sudo tee /etc/containers/systemd/litellm-db.volume >/dev/null <<'EOF'
[Volume]
VolumeName=litellm-db
EOF

sudo tee /etc/containers/systemd/litellm-db.container >/dev/null <<'EOF'
[Unit]
Description=Postgres for LiteLLM

[Container]
ContainerName=litellm-db
Image=docker.io/library/postgres:16.15
Network=litellm.network
Volume=litellm-db.volume:/var/lib/postgresql/data
EnvironmentFile=/opt/litellm/db.env
HealthCmd=pg_isready -U litellm -d litellm
HealthInterval=10s
Notify=healthy

[Service]
Restart=always

[Install]
WantedBy=multi-user.target
EOF

sudo tee /etc/containers/systemd/litellm.container >/dev/null <<'EOF'
[Unit]
Description=LiteLLM AI gateway
Requires=litellm-db.service
After=litellm-db.service

[Container]
ContainerName=litellm
Image=ghcr.io/berriai/litellm:v1.104.0
Network=litellm.network
PublishPort=4000:4000
EnvironmentFile=/opt/litellm/litellm.env
Volume=/opt/litellm/config.yaml:/app/config.yaml:ro,Z
Exec=--config /app/config.yaml --port 4000

[Service]
Restart=always
RestartSec=10
TimeoutStartSec=300

[Install]
WantedBy=multi-user.target
EOF

Start and check it.

sudo systemctl daemon-reload               # turn the Quadlet files into services
sudo systemctl start litellm               # starts litellm-db first; the first start pulls the images
sudo journalctl -u litellm -f              # Ctrl-C once you see "Uvicorn running on http://0.0.0.0:4000"
sudo firewall-cmd --permanent --add-port=4000/tcp && sudo firewall-cmd --reload   # if firewalld is running

curl -s http://192.168.1.101:4000/health/liveliness; echo     # "I'm alive!"
curl -s http://192.168.1.101:4000/health/readiness             # "db": "connected"

Model server: In LM Studio, give the model a default context length of 32k or more (gear icon on the model, then Context Length). LM Studio loads models on demand with that setting, and reasoning ("thinking") models spend tokens thinking before they answer. With a small context they can use it all up and return an empty reply with finish_reason: "length".

The admin UI is at http://192.168.1.101:4000/ui (user admin, the password you chose). The first start runs about 185 database migrations and takes a minute or two.

Part 3: Convert a hand-started container into a Quadlet

If LiteLLM was started with podman run, it isn't a systemd service. With --restart=always and podman-restart.service enabled it does come back after a reboot, but you can't manage it with systemctl, its logs aren't in the journal, and if the container is removed the only record of how it was created is your memory. Converting fixes all three. First, record exactly how it runs now, and keep a copy for rollback:

sudo podman inspect litellm --format 'image={{.Config.Image}}
networks={{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}
ports={{json .HostConfig.PortBindings}}
created with: {{join .Config.CreateCommand " "}}'
sudo podman inspect litellm | sudo tee /opt/litellm/inspect.bak-$(date +%F).json >/dev/null
sudo chmod 600 /opt/litellm/inspect.bak-*.json         # it contains the env, including the master key

Translate what you found into a .container file: -p becomes PublishPort=, -v becomes Volume=, --env-file becomes EnvironmentFile=, each network becomes a Network= line, and the arguments after the image name become Exec=. For example, a container created with podman run -d --name litellm --restart=always -p 4000:4000 -v /opt/litellm/config.yaml:/app/config.yaml:ro,Z --env-file /opt/litellm/litellm.env ghcr.io/berriai/litellm:v1.104.0 --config /app/config.yaml --port 4000, and later connected to a network named docker_default where its database lives, becomes:

sudo tee /etc/containers/systemd/litellm.container >/dev/null <<'EOF'
[Unit]
Description=LiteLLM AI gateway

[Container]
ContainerName=litellm
Image=ghcr.io/berriai/litellm:v1.104.0
Network=podman
Network=docker_default
PublishPort=4000:4000
EnvironmentFile=/opt/litellm/litellm.env
Volume=/opt/litellm/config.yaml:/app/config.yaml:ro,Z
Exec=--config /app/config.yaml --port 4000

[Service]
Restart=always
RestartSec=10
TimeoutStartSec=300

[Install]
WantedBy=multi-user.target
EOF
sudo /usr/libexec/podman/quadlet -dryrun 2>/dev/null | grep ^ExecStart    # the podman run command it will use

Compare that ExecStart line with the original command. When they match, swap the containers. Config, env file and database are untouched; only the container is recreated, so the gateway is down for 20–30 seconds:

sudo podman rm -f litellm
sudo systemctl daemon-reload
sudo systemctl start litellm
sudo podman inspect litellm --format '{{index .Config.Labels "PODMAN_SYSTEMD_UNIT"}}'    # litellm.service
curl -s http://192.168.1.101:4000/health/readiness

Rollback: delete the .container file, run sudo systemctl daemon-reload, and rerun the original podman run command from the inspect output (plus podman network connect for any extra network).

Warning: Check that the database comes back after a reboot too. If LiteLLM's database lives in another app's container that has no systemd service and a restart policy of no, LiteLLM will start after a reboot and find no database. RestartSec=10 keeps it retrying, but the real fix is Part 4.

Quick fix: If converting isn't an option right now, at least make sure the existing container restarts at boot: it needs --restart=always (check with sudo podman inspect litellm --format '{{.HostConfig.RestartPolicy.Name}}') and sudo systemctl enable --now podman-restart.service.

Part 4: Give LiteLLM its own Postgres

LiteLLM works without a database, but then there are no virtual keys, agents, MCP servers stored through the API, or spend logs, so most of these labs won't work. A database inside another application's Postgres works, but ties the gateway to that application: it shares its admin login and starts and stops with it. This part moves LiteLLM to a Postgres of its own, keeping every key and log.

1. Create the new database. Create db.env, litellm.network, litellm-db.volume and litellm-db.container exactly as in Part 2 (skip the parts that write litellm.env, config.yaml and litellm.container), then start only the database. The gateway keeps running on the old one meanwhile.

sudo systemctl daemon-reload
sudo systemctl start litellm-db
sudo podman exec litellm-db psql -U litellm -d litellm -c 'select version();'

2. Copy the data. Stop LiteLLM so nothing is written during the copy, then dump the old database and load it into the new one. The example assumes the old database is litellm in a container named postgresdb with the admin user admin; check yours with sudo grep DATABASE_URL /opt/litellm/litellm.env. --no-owner --no-privileges leaves out the old server's user names, so everything ends up owned by the new litellm user.

sudo systemctl stop litellm                # or: sudo podman stop litellm
sudo podman exec postgresdb pg_dump -U admin -d litellm --no-owner --no-privileges \
  | sudo tee /opt/litellm/litellm-db-$(date +%F).sql >/dev/null
sudo chmod 600 /opt/litellm/litellm-db-*.sql
sudo cat /opt/litellm/litellm-db-$(date +%F).sql \
  | sudo podman exec -i litellm-db psql -q -v ON_ERROR_STOP=1 -U litellm -d litellm >/dev/null && echo restored

Check that the important tables arrived with the same number of rows (run each line against both databases):

for t in LiteLLM_VerificationToken LiteLLM_SpendLogs LiteLLM_AgentsTable _prisma_migrations; do
  old=$(sudo podman exec postgresdb psql -U admin   -d litellm -Atc "select count(*) from \"$t\"")
  new=$(sudo podman exec litellm-db psql -U litellm -d litellm -Atc "select count(*) from \"$t\"")
  echo "$t  old=$old  new=$new"
done

3. Point LiteLLM at it. Change DATABASE_URL in the env file to the new database, using the password from db.env. Then make the Quadlet start after the database and join its network. You can drop the old database's network if LiteLLM only used it for the database.

sudo cp -a /opt/litellm/litellm.env /opt/litellm/litellm.env.bak-$(date +%F)
P=$(sudo grep ^POSTGRES_PASSWORD /opt/litellm/db.env | cut -d= -f2)
sudo sed -i "s#^DATABASE_URL=.*#DATABASE_URL=postgresql://litellm:$P@litellm-db:5432/litellm#" /opt/litellm/litellm.env
unset P
sudo vi /etc/containers/systemd/litellm.container
#   under [Unit]:       Requires=litellm-db.service
#                       After=litellm-db.service
#   under [Container]:  Network=litellm.network   (replacing the old database's network)
sudo systemctl daemon-reload
sudo systemctl start litellm
curl -s http://192.168.1.101:4000/health/readiness                # "db": "connected"

Make a request or two, then check that the newest spend log row is in the new database: sudo podman exec litellm-db psql -U litellm -d litellm -Atc 'select max("startTime") from "LiteLLM_SpendLogs"'. Once you're satisfied, drop the old copy (sudo podman exec postgresdb dropdb -U admin litellm) and keep the dump file as a backup.

Other options: An external Postgres (a database server, a managed service) works the same way: create a database and user there, point DATABASE_URL at it, and leave out the litellm-db files and the Requires= line.

Part 5: Upgrades, backups and options

Which change needs what.

You changedRun
config.yaml or litellm.envsudo systemctl restart litellm (a Quadlet restart creates a fresh container, so env file changes are picked up)
A .container, .network or .volume filesudo systemctl daemon-reload, then restart the service
Keys, agents, MCP servers (through the API or UI)Nothing; they're stored in the database and take effect at once

Back up the database before every upgrade, and on a schedule if the spend logs matter to you:

sudo podman exec litellm-db pg_dump -U litellm litellm | sudo tee /opt/litellm/backup-$(date +%F).sql >/dev/null
sudo chmod 600 /opt/litellm/backup-*.sql

Upgrade LiteLLM by changing the image tag. Read the release notes for the versions you're skipping first; LiteLLM runs its own database migrations at startup.

sudo sed -i 's#litellm:v1.104.0#litellm:v1.105.0#' /etc/containers/systemd/litellm.container
sudo systemctl daemon-reload && sudo systemctl restart litellm      # pulls the new image, then migrates
curl -s http://192.168.1.101:4000/openapi.json | jq -r .info.version
  • Pin the version. A floating tag such as main-stable or latest means you can't tell which build you run, and a pull can silently change it. Compromised LiteLLM releases were published to PyPI in March 2026, so know exactly what you run. For full reproducibility, pin the digest: Image=ghcr.io/berriai/litellm@sha256:... (sudo podman image inspect --format '{{index .RepoDigests 0}}' <image> prints it).
  • Cloud models go in model_list the same way: model: anthropic/claude-haiku-4-5-20251001 with api_key: os.environ/ANTHROPIC_API_KEY, or model: openai/gpt-4.1-mini with api_key: os.environ/OPENAI_API_KEY, and the key itself in litellm.env.
  • LITELLM_SALT_KEY encrypts provider keys you store through the UI. Never change it after that, or LiteLLM can't decrypt them. Older installs without one use the master key, which then mustn't change either.
  • :Z on a mount relabels the file for SELinux. Without it the container gets "permission denied" reading config.yaml.
  • Without Podman: pip install 'litellm[proxy]==1.104.0' in a Python 3.12 venv runs the same gateway with litellm --config config.yaml --port 4000. You then write your own systemd unit to keep it running.
  • Production extras these labs don't need: Redis (shared rate limits and caching across several LiteLLM instances), and a reverse proxy with TLS in front of port 4000.

Lab 1: Connect to the Gateway and Add the Lab Model Names

192.168.1.100 → 192.168.1.101

Goalset up your shell on the agent host, confirm the gateway is healthy, has a database and survives reboots, then give it two new model names, lab-chat and lab-agent, that every later lab uses.

1. Your shell on the agent host

You type every command from here on on 192.168.1.100 unless a step says otherwise. Two shell variables hold the gateway address and the master key, LiteLLM's admin password. Whoever runs the gateway has it; on .101 it's in /opt/litellm/litellm.env. read -rsp reads it without echoing it or saving it in your shell history.

ssh 192.168.1.100
sudo dnf -y install jq                     # pretty-prints and filters JSON answers
export GW=http://192.168.1.101:4000
read -rsp 'LiteLLM master key: ' MK; echo; export MK

Tip: Put the export GW=... line in ~/.bashrc so new shells have it. Don't do that with the master key; re-enter it when you need it.

2. Is it up, and does it have a database?

curl -s $GW/health/liveliness; echo                        # "I'm alive!" (no key needed)
curl -s $GW/health/readiness | jq '{status, db}'            # db must be "connected"
curl -s $GW/openapi.json | jq -r .info.version              # the LiteLLM version

/health/liveliness only says the process is running. /health/readiness also checks the database, which the labs need from Lab 3 on: virtual keys, agents and spend logs all live there. If db isn't connected, see Lab 0, Part 4.

3. Will it come back after a reboot?

On .101, ask Podman whether the container belongs to a systemd service. This only reads:

ssh 192.168.1.101
sudo podman inspect litellm --format 'unit={{index .Config.Labels "PODMAN_SYSTEMD_UNIT"}} restart={{.HostConfig.RestartPolicy.Name}}'
systemctl is-active litellm-db 2>/dev/null; systemctl is-enabled podman-restart.service
What you seeMeansDo
unit=litellm.serviceIt's a Quadlet (or other systemd) serviceNothing.
unit= (empty), restart=always, podman-restart enabledStarted by hand; comes back at boot through podman-restart.serviceWorks. Lab 0, Part 3 converts it to a Quadlet.
unit= (empty), anything elseIt won't come back after a rebootLab 0, Part 3.

Its database has to come back too. active for litellm-db means it has its own Postgres service, as in Lab 0. Anything else: find the database host in DATABASE_URL and check that it starts at boot.

4. Add the two lab model names

Look at the models the gateway serves now:

curl -s $GW/v1/models -H "Authorization: Bearer $MK" | jq -r '.data[].id'
# qwen3.8-27b
# ...

Every later lab asks for one of two names: lab-chat (chat apps) or lab-agent (agents, which need a model that can call tools). Neither is a new model. Each is an extra model_list entry, an alias, that forwards to a model you already have. Using aliases has two benefits:

  • The lab commands work unchanged whatever model you run. You map the two names to your model once, here.
  • It's how a gateway is meant to be used. Apps ask for a role, not a specific model, so you can later move lab-agent to a bigger model or a cloud provider by changing one line, and no app or agent has to change.

On .101, back up the config and open it:

ssh 192.168.1.101
sudo cp -a /opt/litellm/config.yaml /opt/litellm/config.yaml.bak-$(date +%F)
sudo vi /opt/litellm/config.yaml

Add these two entries at the end of the existing model_list, indented like the entries already there. Both use the same real model as an existing entry (qwen/qwen3.8-27b here; use your own model's id). Only model_name is new:

  - model_name: lab-chat                   # the name chat apps ask for
    litellm_params:
      model: openai/qwen/qwen3.8-27b       # the real model it forwards to
      api_base: os.environ/LMSTUDIO_API_BASE
      api_key: not-needed
  - model_name: lab-agent                  # the name agents ask for
    litellm_params:
      model: openai/qwen/qwen3.8-27b
      api_base: os.environ/LMSTUDIO_API_BASE
      api_key: not-needed

LiteLLM reads its config only at startup, so restart it. The gateway is down for about 20 seconds:

sudo systemctl restart litellm             # or "sudo podman restart litellm" if it isn't a Quadlet service
sudo journalctl -u litellm -f              # Ctrl-C once you see "Uvicorn running"

Verify (back on .100)

curl -s $GW/v1/models -H "Authorization: Bearer $MK" | jq -r '.data[].id' | grep lab-
# lab-chat
# lab-agent

curl -s $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "lab-agent", "messages": [{"role": "user", "content": "Say hi in five words."}]}' \
  | jq '{model, answer: .choices[0].message.content}'

The answer comes from qwen3.8-27b, but the response says "model": "lab-agent": the client only ever sees the alias.

Notes

  • Both names point at the same model on purpose. On a single GPU, alternating between two large models makes LM Studio unload one and load the other, and every request waits for the load.
  • YAML is indentation-sensitive, and each top-level key (model_list:, litellm_settings:) may appear only once. If LiteLLM won't start after the edit, sudo journalctl -u litellm -n 50 shows the error; copy the backup back and restart to get going again.
  • If the reply is empty and finish_reason is "length", the model ran out of context while thinking. Raise its context length in LM Studio (Lab 0, Part 2 has the note).
  • Don't open /health on its own (without /liveliness or /readiness). It sends a real request to every model the gateway serves, which makes LM Studio load each one in turn and can stall everyone else using it.
  • The admin UI at http://192.168.1.101:4000/ui shows the same information under Models and Settings.

Goalunderstand a chat request and its response, see why a chat client has to send the whole conversation every time, and build a small streaming chat program in Python.

1. One request, piece by piece

curl -s $GW/v1/chat/completions \
  -H "Authorization: Bearer $MK" \
  -H 'Content-Type: application/json' \
  -d '{
        "model": "lab-chat",
        "messages": [
          {"role": "system", "content": "You are a helpful assistant. Answer in one sentence."},
          {"role": "user",   "content": "What does an AI gateway do?"}
        ]
      }' | jq
  • /v1/chat/completions is the OpenAI chat API. LiteLLM speaks it no matter which provider is behind the alias, so any OpenAI-compatible app or library can use the gateway.
  • Authorization: Bearer carries the key. The master key works for now; Lab 3 gives each app its own key.
  • messages is the conversation: a system message sets the behaviour, and user messages are what you type.

In the response, the answer is in choices[0].message.content, usage counts the tokens in and out, and model is the alias you asked for. To print just the answer, replace jq with jq -r '.choices[0].message.content'.

2. The API has no memory

Ask a follow-up question on its own and the model has no idea what you mean:

curl -s $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "lab-chat", "messages": [{"role": "user", "content": "What did I just ask you?"}]}' \
  | jq -r '.choices[0].message.content'

Every chat app, including ChatGPT-style web UIs, keeps the conversation itself and sends the whole history with every request, adding the model's earlier answers as assistant messages:

curl -s $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "lab-chat", "messages": [
        {"role": "user",      "content": "My favourite distro is Rocky Linux."},
        {"role": "assistant", "content": "Nice choice!"},
        {"role": "user",      "content": "What is my favourite distro?"}
      ]}' | jq -r '.choices[0].message.content'

That's also why long conversations get slower and more expensive: every turn re-sends everything before it.

3. Streaming

With "stream": true, the gateway sends the answer in small pieces as the model produces them, the way chat UIs show text appearing word by word. curl -N turns off buffering so you see them arrive:

curl -sN $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "lab-chat", "stream": true, "messages": [{"role": "user", "content": "Count from 1 to 5."}]}'
# data: {"choices":[{"delta":{"content":"1"}...}]}
# data: {"choices":[{"delta":{"content":","}...}]}
# ...
# data: [DONE]

cat > ~/gw-labs/chat.py <<'EOF'
"""chat.py: a terminal chat client. Every message goes through the LiteLLM gateway."""
import os

from openai import OpenAI

client = OpenAI(base_url=os.environ["GW"] + "/v1", api_key=os.environ["KEY"])
MODEL = os.environ.get("MODEL", "lab-chat")

# The API has no memory. The conversation lives in this list, and the
# whole list is sent with every request.
history = [{"role": "system", "content": "You are a helpful assistant. Keep answers short."}]

print(f"Chatting with {MODEL} through {os.environ['GW']}. Ctrl-D to quit.")
while True:
    try:
        question = input("\nyou> ").strip()
    except EOFError:
        break
    if not question:
        continue
    history.append({"role": "user", "content": question})

    stream = client.chat.completions.create(model=MODEL, messages=history, stream=True)
    print("ai > ", end="", flush=True)
    answer = ""
    for chunk in stream:                       # print each piece as it arrives
        piece = chunk.choices[0].delta.content if chunk.choices else None
        if not piece:
            continue
        answer += piece
        print(piece, end="", flush=True)
    print()
    history.append({"role": "assistant", "content": answer})
EOF
KEY=$MK python chat.py
# you> My name is Pat.
# ai > Hi Pat! How can I help you today?
# you> What is my name?
# ai > Your name is Pat.

  • The admin UI at http://192.168.1.101:4000/ui has a Playground page that does the same thing in the browser.
  • If a request hangs for a minute and then answers, LM Studio was loading the model. The first request after a model unloads is always slow.

Lab 3: Virtual Keys: One Key per App

192.168.1.100 → 192.168.1.101

Goalstop handing out the master key: create a virtual key for the chat UI that can only use the lab models, and see the gateway enforce it.

Why

The master key can do everything, including creating and deleting keys. Every app and agent in these labs gets its own virtual key instead. A virtual key can be limited to certain models, a request rate, a budget, and (Labs 7–9) certain agents and tools. Every request is logged under the key's name, and you can revoke one key without touching the others.

1. Create a key for the chat UI

curl -s $GW/key/generate -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{
        "key_alias": "chat-ui",
        "models": ["lab-chat", "lab-agent"],
        "rpm_limit": 60
      }' | jq '{key_alias, key, models, rpm_limit}'
  • key_alias is the name you'll see in logs and in the UI. It must be unique: re-running a step that creates a key fails with "Key with alias ... already exists", so delete the old key (Lab 11) or pick another alias.
  • models is the allow-list. Leave it out and the key can use every model.
  • rpm_limit is requests per minute. Request number 61 inside a minute gets HTTP 429.

Copy the key value now. LiteLLM stores only a hash of it, so it can never show you the key again. Keep it in a variable for this lab:

read -rsp 'chat-ui key: ' UIKEY; echo

2. See the limits work

curl -s $GW/v1/chat/completions -H "Authorization: Bearer $UIKEY" -H 'Content-Type: application/json' \
  -d '{"model": "lab-chat", "messages": [{"role": "user", "content": "Say hello."}]}' \
  | jq -r '.choices[0].message.content'

# a model that isn't on the key's list: refused before it reaches any model
curl -s $GW/v1/chat/completions -H "Authorization: Bearer $UIKEY" -H 'Content-Type: application/json' \
  -d '{"model": "gemma-4-31b-qat", "messages": [{"role": "user", "content": "Say hello."}]}' \
  | jq -r '.error.message'
# ... key not allowed to access model ...

# the key can't do admin work either
curl -s $GW/key/generate -H "Authorization: Bearer $UIKEY" -H 'Content-Type: application/json' -d '{}' | jq -r '.error.message'

3. Look a key up, change it, block it

curl -s "$GW/key/info?key=$UIKEY" -H "Authorization: Bearer $MK" | jq '.info | {key_alias, models, rpm_limit, spend}'

# change a limit in place (the key itself stays the same)
curl -s $GW/key/update -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \

Lab 5: Agent 1: Your First Tool-Using Agent

192.168.1.100 → 192.168.1.101

Goalbuild ops-agent, a small Python agent that answers questions about the lab by calling tools (check a URL, check a port, get the time), and see exactly what makes something an "agent".

What makes it an agent

A chat model only produces text. An agent is a loop around the model that lets it do things:

  1. You send the question, plus a description of each tool: its name, what it does, and its parameters as JSON Schema.
  2. Instead of answering, the model can reply with a tool call: "run check_port with host=192.168.1.101, port=22".
  3. Your code runs that function and sends the result back as a tool message.
  4. Repeat until the model replies with plain text. That's the answer.

The model never runs anything itself; your code decides which functions exist and runs them. Every step of the loop is an ordinary chat request through the gateway.

1. A key for the agent

curl -s $GW/key/generate -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"key_alias": "ops-agent", "models": ["lab-agent"], "rpm_limit": 30}' | jq -r .key
read -rsp 'ops-agent key: ' OPS_KEY; echo

2. The agent

cat > ~/gw-labs/agent.py <<'EOF'
"""ops-agent: a small tool-using agent. Every model call goes through the LiteLLM gateway."""
import json
import os
import socket
import sys
import time
from datetime import datetime, timezone

import httpx
from openai import OpenAI

client = OpenAI(base_url=os.environ["GW"] + "/v1", api_key=os.environ["AGENT_KEY"])
MODEL = os.environ.get("AGENT_MODEL", "lab-agent")


# ---- the tools: plain Python functions -------------------------------------
def get_time() -> str:
    return datetime.now(timezone.utc).isoformat(timespec="seconds")


def check_url(url: str) -> str:
    start = time.monotonic()
    try:
        r = httpx.get(url, timeout=5, follow_redirects=True)
        return f"HTTP {r.status_code} in {(time.monotonic() - start) * 1000:.0f} ms"
    except httpx.HTTPError as err:
        return f"failed: {err!r}"


def check_port(host: str, port: int) -> str:
    try:
        with socket.create_connection((host, int(port)), timeout=3):
            return f"{host}:{port} is open"
    except OSError as err:
        return f"{host}:{port} is closed or unreachable ({err})"


TOOLS = {"get_time": get_time, "check_url": check_url, "check_port": check_port}

# ---- how the model learns about the tools: JSON Schema descriptions --------
TOOL_SPECS = [
    {"type": "function", "function": {
        "name": "get_time", "description": "Current date and time in UTC.",
        "parameters": {"type": "object", "properties": {}}}},
    {"type": "function", "function": {
        "name": "check_url", "description": "Fetch a URL and report the HTTP status and response time.",
        "parameters": {"type": "object", "properties": {"url": {"type": "string"}}, "required": ["url"]}}},
    {"type": "function", "function": {
        "name": "check_port", "description": "Test whether a TCP port on a host accepts connections.",
        "parameters": {"type": "object", "properties": {"host": {"type": "string"}, "port": {"type": "integer"}},
                       "required": ["host", "port"]}}},
]

# A2A services (Lab 6) reuse this file and override these two settings per agent.
SYSTEM = os.environ.get("AGENT_PROMPT", "You are ops-agent, a home-lab operations assistant. "
                        "Use the tools to check facts instead of guessing. Answer briefly.")
USE_TOOLS = os.environ.get("AGENT_TOOLS", "on") == "on"


# ---- the agent loop ---------------------------------------------------------
def run(question: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}]
    for _ in range(max_steps):
        extra = {"tools": TOOL_SPECS} if USE_TOOLS else {}
        reply = client.chat.completions.create(model=MODEL, messages=messages, **extra)
        msg = reply.choices[0].message
        if not msg.tool_calls:                      # no tool requested: this is the answer
            return msg.content
        messages.append(msg.model_dump(exclude_none=True))
        for call in msg.tool_calls:                 # run each requested tool, return the result
            args = json.loads(call.function.arguments or "{}")
            result = TOOLS[call.function.name](**args)
            print(f"  [tool] {call.function.name}({args}) -> {result}", file=sys.stderr)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return "Stopped: too many steps."


if __name__ == "__main__":
    print(run(" ".join(sys.argv[1:]) or "Is the gateway at 192.168.1.101 port 4000 up, and what time is it?"))
EOF

Read it top to bottom: the tools are plain Python functions, TOOL_SPECS describes them to the model, and run() is the loop. max_steps stops a confused model from looping forever. The two settings near the middle (AGENT_PROMPT, AGENT_TOOLS) let Lab 6 reuse this file for a second agent.

Lab 6: Agent 2: Run Agents as Always-On Services

Goalpackage the agent in a container image, run two agents from it as Quadlet services (ops-agent with tools and writer-agent without), each with its own key, and talk to them over A2A.

A2A in one paragraph

A script is only useful to the person running it. To let other programs and other agents use an agent, it needs a network interface. A2A (Agent2Agent) is an open protocol for that. An A2A agent publishes an agent card, a JSON description of who it is and what it can do, at /.well-known/agent-card.json, and accepts messages as JSON-RPC SendMessage calls over HTTP. LiteLLM understands A2A, which is what Lab 7 uses.

1. The A2A wrapper

This file turns the Lab 5 agent into an A2A server. It imports agent.py unchanged and calls agent.run() for every message that arrives. Settings come from environment variables, so one image can be several agents.

sudo mkdir -p /opt/agents
sudo cp ~/gw-labs/agent.py /opt/agents/
sudo tee /opt/agents/a2a_server.py >/dev/null <<'EOF'
"""Serve the agent from agent.py over A2A (Agent2Agent), so other agents can call it."""
import asyncio
import os

import uvicorn
from a2a.helpers import get_message_text, new_task_from_user_message, new_text_message, new_text_part
from a2a.server.agent_execution import AgentExecutor, RequestContext
from a2a.server.events import EventQueue
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.routes import create_agent_card_routes, create_jsonrpc_routes
from a2a.server.tasks import InMemoryTaskStore, TaskUpdater
from a2a.types import AgentCapabilities, AgentCard, AgentInterface, AgentSkill, TaskState
from starlette.applications import Starlette

import agent  # the Lab 5 agent: agent.run(question) -> answer

NAME = os.environ.get("AGENT_NAME", "ops-agent")
DESCRIPTION = os.environ.get("AGENT_DESCRIPTION", "Checks home-lab hosts, ports and URLs.")
PORT = int(os.environ.get("PORT", "8601"))
PUBLIC_URL = os.environ["PUBLIC_URL"]  # how other hosts reach this agent, e.g. http://192.168.1.100:8601


class Executor(AgentExecutor):
    async def execute(self, context: RequestContext, event_queue: EventQueue) -> None:
        task = context.current_task or new_task_from_user_message(context.message)
        if not context.current_task:
            await event_queue.enqueue_event(task)
        updater = TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id)
        await updater.update_status(state=TaskState.TASK_STATE_WORKING, message=new_text_message("Working..."))

        answer = await asyncio.to_thread(agent.run, get_message_text(context.message) or "")

        await updater.add_artifact(parts=[new_text_part(text=answer, media_type="text/plain")])
        await updater.update_status(state=TaskState.TASK_STATE_COMPLETED, message=new_text_message(answer))

    async def cancel(self, context: RequestContext, event_queue: EventQueue) -> None:
        raise NotImplementedError


card = AgentCard(
    name=NAME,
    description=DESCRIPTION,
    version="1.0.0",
    default_input_modes=["text/plain"],
    default_output_modes=["text/plain"],
    capabilities=AgentCapabilities(streaming=False),
    supported_interfaces=[AgentInterface(protocol_binding="JSONRPC", url=PUBLIC_URL, protocol_version="1.0")],
    skills=[AgentSkill(id=NAME, name=NAME, description=DESCRIPTION, tags=["lab"])],
)
handler = DefaultRequestHandler(agent_executor=Executor(), task_store=InMemoryTaskStore(), agent_card=card)
app = Starlette(routes=[*create_agent_card_routes(card), *create_jsonrpc_routes(handler, "/")])

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=PORT)
EOF

Lab 8: Agent 4: Tools from an MCP Server, Through the Gateway

192.168.1.100 (MCP server, agent) and 192.168.1.101

Goalmove the lab tools out of the agent into an MCP server running as a Quadlet, register it with LiteLLM, and build an agent that finds its tools through the gateway.

MCP in one paragraph

In Lab 5 the tools were written into the agent. MCP (Model Context Protocol) moves tools into a separate server that any agent or app can connect to and ask "what tools do you have?". Register MCP servers with LiteLLM, and agents connect to one endpoint, http://192.168.1.101:4000/mcp/, with their virtual key. They see only the tools that key has been granted, and every tool call is logged.

1. The MCP server

The mcp library turns plain Python functions into MCP tools; the docstring becomes the tool description the model reads.

sudo mkdir -p /opt/lab-tools
sudo tee /opt/lab-tools/lab_tools.py >/dev/null <<'EOF'
"""lab-tools: an MCP server that exposes home-lab checks as tools."""
import socket
import time

import httpx
from mcp.server.mcpserver import MCPServer

mcp = MCPServer("lab-tools")


@mcp.tool()
def check_url(url: str) -> str:
    """Fetch a URL and report the HTTP status and response time."""
    start = time.monotonic()
    try:
        r = httpx.get(url, timeout=5, follow_redirects=True)
        return f"HTTP {r.status_code} in {(time.monotonic() - start) * 1000:.0f} ms"
    except httpx.HTTPError as err:
        return f"failed: {err!r}"


@mcp.tool()
def check_port(host: str, port: int) -> str:
    """Test whether a TCP port on a host accepts connections."""
    try:
        with socket.create_connection((host, port), timeout=3):
            return f"{host}:{port} is open"
    except OSError as err:
        return f"{host}:{port} is closed or unreachable ({err})"


@mcp.tool()
def dns_lookup(name: str) -> str:
    """Resolve a host name to its IP addresses."""
    try:
        return ", ".join(sorted({ai[4][0] for ai in socket.getaddrinfo(name, None)}))
    except OSError as err:
        return f"lookup failed: {err}"


if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8701)
EOF

COPY lab_tools.py /app/lab_tools.py

EXPOSE 8701
CMD ["python", "/app/lab_tools.py"]
EOF

"""mcp-agent: an agent that gets its tools from the gateway's MCP endpoint.

The agent has no tools of its own. It asks LiteLLM which MCP tools its key may
use, hands them to the model, and runs the model's tool calls through LiteLLM.
"""
import asyncio
import json
import os
import sys

import httpx2
from mcp import Client
from mcp.client.streamable_http import streamable_http_client
from openai import OpenAI

GW, KEY = os.environ["GW"], os.environ["AGENT_KEY"]
llm = OpenAI(base_url=GW + "/v1", api_key=KEY)
SYSTEM = "You are a home-lab operations assistant. Use the tools to check facts. Answer briefly."


async def main(question: str) -> None:
    http = httpx2.AsyncClient(headers={"Authorization": f"Bearer {KEY}"}, timeout=60)
    async with Client(streamable_http_client(GW + "/mcp/", http_client=http)) as mcp:
        tools = (await mcp.list_tools()).tools
        print("tools from the gateway:", [t.name for t in tools], file=sys.stderr)
        specs = [{"type": "function", "function": {
            "name": t.name, "description": t.description or "", "parameters": t.input_schema}} for t in tools]

        messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}]
        for _ in range(8):
            msg = llm.chat.completions.create(model="lab-agent", messages=messages, tools=specs).choices[0].message
            if not msg.tool_calls:
                print(msg.content)
                return
            messages.append(msg.model_dump(exclude_none=True))
            for call in msg.tool_calls:
                args = json.loads(call.function.arguments or "{}")
                result = await mcp.call_tool(call.function.name, args)
                text = "\n".join(c.text for c in result.content if c.type == "text")
                print(f"  [mcp] {call.function.name}({args}) -> {text}", file=sys.stderr)
                messages.append({"role": "tool", "tool_call_id": call.id, "content": text})


if __name__ == "__main__":
    asyncio.run(main(" ".join(sys.argv[1:]) or "What IP does rocky-linux resolve to, and is port 4000 open on 192.168.1.101?"))
EOF

Lab 9: Agent 5: A Coordinator That Delegates to Other Agents

192.168.1.100 → 192.168.1.101 → agents on .100

Goalbuild a coordinator agent that can't check anything itself. It asks the gateway which agents it may use, splits the job up, and delegates each part over A2A: checks to ops-agent, the write-up to writer-agent.

How it works

The coordinator is the same loop as Lab 5 with a single tool, ask_agent(agent, message). The list of agents isn't hard-coded. It comes from /v1/agents, so the coordinator sees exactly the agents its key was granted, with their descriptions, and the model picks one by reading those descriptions. Every hop goes through the gateway: the coordinator's own model calls, its calls to other agents, and those agents' model calls.

curl -s $GW/key/generate -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \

read -rsp 'coordinator key: ' COORD_KEY; echo

2. The coordinator

cat > ~/gw-labs/coordinator.py <<'EOF'
"""coordinator: an agent whose only tool is "ask another agent" through the gateway."""
import json
import os
import sys
import uuid

import httpx
from openai import OpenAI

GW, KEY = os.environ["GW"], os.environ["AGENT_KEY"]
llm = OpenAI(base_url=GW + "/v1", api_key=KEY)
auth = {"Authorization": f"Bearer {KEY}"}


def list_agents() -> dict:
    """Ask the gateway which agents this key can see: {name: description}."""
    r = httpx.get(f"{GW}/v1/agents", headers=auth, timeout=30)
    r.raise_for_status()
    return {a["agent_name"]: a["agent_card_params"].get("description", "") for a in r.json()}


def ask_agent(agent: str, message: str) -> str:
    """Send one A2A message to an agent through the gateway and return its reply text."""
    body = {"jsonrpc": "2.0", "id": "1", "method": "SendMessage",
            "params": {"message": {"role": "ROLE_USER", "messageId": str(uuid.uuid4()),
                                   "parts": [{"text": message}]}}}
    r = httpx.post(f"{GW}/a2a/{agent}", json=body, headers={**auth, "A2A-Version": "1.0"}, timeout=300)
    data = r.json()
    if "error" in data:
        return f"error from {agent}: {data['error']}"
    task = data["result"]["task"]
    return "\n".join(p.get("text", "") for p in task["status"]["message"]["parts"])


def main(goal: str) -> None:
    agents = list_agents()
    print("agents on the gateway:", list(agents), file=sys.stderr)
    if not agents:
        sys.exit("This key isn't allowed to use any agents.")
    roster = "\n".join(f"- {name}: {desc}" for name, desc in agents.items())
    tools = [{"type": "function", "function": {
        "name": "ask_agent", "description": "Delegate a task to one of the available agents.",
        "parameters": {"type": "object", "required": ["agent", "message"], "properties": {
            "agent": {"type": "string", "enum": list(agents)},
            "message": {"type": "string", "description": "A complete, self-contained request."}}}}}]
    messages = [
        {"role": "system", "content": "You are a coordinator. You cannot check anything yourself. "
                                      "Break the goal into steps and delegate each step to the best agent:\n" + roster},
        {"role": "user", "content": goal}]
    for _ in range(8):
        msg = llm.chat.completions.create(model="lab-agent", messages=messages, tools=tools).choices[0].message
        if not msg.tool_calls:
            print(msg.content)
            return
        messages.append(msg.model_dump(exclude_none=True))
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            print(f"  -> {args['agent']}: {args['message']}", file=sys.stderr)
            answer = ask_agent(**args)
            print(f"  <- {args['agent']}: {answer[:200]}", file=sys.stderr)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": answer})


if __name__ == "__main__":
    main(" ".join(sys.argv[1:]) or "Check whether the gateway (http://192.168.1.101:4000/health/liveliness) "
                                    "and SSH on 192.168.1.100 are up, then have the results written up as a status update.")
EOF

Two details worth noticing. The enum in the tool's parameters limits the model to agent names that actually exist. The system prompt says it can't check anything itself, which stops it guessing instead of delegating.

  | jq -r '.content[] | select(.type == "text") | .text'

  • A local 27B model is fine for trying this out and for small edits. For serious work on a big codebase, put a larger or cloud model behind a separate alias and add it to this key's models.
  • Both agents can run shell commands on the machine they run on. Keep their permission prompts on ("permission": {"bash": "ask"} in opencode); the gateway controls model access, not what the agent does locally.

2. The reboot test

This is the real proof. Reboot the agent host, and then the gateway:

sudo systemctl reboot                      # on .100; reconnect after a minute
systemctl is-active open-webui ops-agent writer-agent lab-tools    # all "active"
curl -s http://localhost:8601/.well-known/agent-card.json | jq -r .name

# on .101
sudo systemctl reboot
curl -s http://192.168.1.101:4000/health/readiness | jq '{status, db}'

If a service isn't active, check that its file is in /etc/containers/systemd/, that it has an [Install] section with WantedBy=multi-user.target, and run sudo /usr/libexec/podman/quadlet -dryrun to see Quadlet's complaints about any file it couldn't convert.

3. Logs

sudo journalctl -u ops-agent -f                 # one service, live
sudo journalctl -u litellm --since '10 min ago' # on .101: gateway errors, model failures
sudo journalctl -b -u 'ops-agent' -u 'lab-tools' --no-pager   # everything since the last boot

A Quadlet container's output goes to the journal, so you use journalctl, not podman logs (which still works too).

4. Who used what

curl -s "$GW/spend/logs?start_date=$(date -u -d '7 days ago' +%F)&end_date=$(date -u -d tomorrow +%F)&summarize=false" \
  -H "Authorization: Bearer $MK" \
  | jq -r 'group_by(.metadata.user_api_key_alias)[]

The gateway UI shows the same under Usage (charts per key and model) and Logs (each request, with its prompt and response).

5. Kill switch

# block one key: every request with it fails right away, and nothing else is affected
curl -s $GW/key/block   -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' -d "{\"key\": \"$OPS_KEY\"}" | jq '{key_alias, blocked}'
curl -s $GW/key/unblock -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' -d "{\"key\": \"$OPS_KEY\"}" | jq '{key_alias, blocked}'

# delete a key for good
curl -s $GW/key/delete  -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' -d "{\"keys\": [\"$CALLER_KEY\"]}"

# stop an agent from being reachable through the gateway
curl -s -X DELETE $GW/v1/agents/<agent_id> -H "Authorization: Bearer $MK"

Blocking ops-agent's key stops that agent from reaching any model, even when someone calls it directly on port 8601. That's the advantage of agents having their own keys instead of sharing one.

6. Upgrades

An agent: edit the code in /opt/agents, rebuild with a new tag, point the Quadlet at it, restart. Keeping the old tag makes rolling back a one-line change.

sudo podman build -t localhost/a2a-agent:2 /opt/agents
sudo sed -i 's#localhost/a2a-agent:1#localhost/a2a-agent:2#' /etc/containers/systemd/{ops,writer}-agent.container
sudo systemctl daemon-reload && sudo systemctl restart ops-agent writer-agent

Upgrading LiteLLM itself, and backing up its database, are in Lab 0, Part 5.
