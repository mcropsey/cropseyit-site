LiteLLM AI Gateway Labs

Hands-on labs for running an AI gateway in a two-host home lab: one API for many models, fallbacks, virtual keys and budgets, caching, guardrails, observability, MCP, Claude Code and A2A agents.

Hosts: docker = 192.168.1.100 (Postgres, Redis, Langfuse, the A2A agent) | gateway = 192.168.1.101 (an existing LiteLLM proxy on port 4000) | workstation = wherever you run curl, jq and the check scripts.

These labs assume LiteLLM is already running and add to it rather than replacing it. Lab 1 is read-only, Lab 2 only touches .100, and Lab 3 is the one change window on .101, with a backup taken first and a rollback in Appendix B. Labs 4–13 exercise what Lab 3 turned on, and each ends with a small check script so you can re-run every lab at once (Appendix A).

Ground rules

  • Look before you change. Don't modify or restart the existing LiteLLM until you've read its config (Lab 1) and backed it up (Lab 3).
  • Never print a key in full. Read secrets with read -rsp so they stay out of shell history, and show only the last four characters: echo "****${KEY: -4}".
  • Pin every image. No latest, main-stable or bare major tags. LiteLLM had a PyPI supply-chain incident in March 2026, so know exactly which build you run and pin it by version or digest.
  • Use real IPs across hosts. From .101, the services on .100 are 192.168.1.100. Inside a container, localhost and host.docker.internal point at that container or its own host, never at the other machine.
  • One phase at a time. Finish a lab, verify it, then move on. If something fails, find out whether it's networking, config, version or license tier before you change anything.

What you need

  • SSH with sudo on both hosts. Docker with the Compose plugin on .100. LiteLLM on .101 (Docker, Podman, systemd or a venv; Lab 1 finds out which).
  • An OpenAI API key and an Anthropic API key for the gpt-mini and claude-fast aliases. No cloud keys? Point both aliases at local models instead (see Lab 3 notes); everything except the provider names still works.
  • On the workstation: curl, jq and bash. Python 3 is optional (Lab 4).
  • LiteLLM 1.80 or newer for the A2A gateway. These labs were written against v1.103.0. All features used here are in the open-source build; none need an enterprise license.

Workstation setup (do this once per shell)

Every check script sources a shared labs/common.sh. Create it now, then export the gateway URL and master key in each new shell.

mkdir -p ~/litellm-labs/labs && cd ~/litellm-labs
cat > labs/common.sh <<'EOF'
# labs/common.sh: sourced by every check script
GW=${GW:-http://192.168.1.101:4000}
: "${MK:?set the master key first: read -rsp 'Master key: ' MK; export MK}"
OUT=${TMPDIR:-/tmp}/litellm-lab.$$.json
HDR=${TMPDIR:-/tmp}/litellm-lab.$$.hdr
trap 'rm -f "$OUT" "$HDR"' EXIT
mask() { printf '****%s' "${1: -4}"; }
# chat KEY MODEL PROMPT [EXTRA_JSON]: prints the HTTP code; body in $OUT, headers in $HDR
chat() {
  local extra=${4:-}; [ -n "$extra" ] || extra='{}'
  curl -s -o "$OUT" -D "$HDR" -w '%{http_code}' "$GW/v1/chat/completions" \
    -H "Authorization: Bearer $1" -H 'Content-Type: application/json' \
    -d "$(jq -n --arg m "$2" --arg p "$3" --argjson x "$extra" \
          '{model:$m, messages:[{role:"user", content:$p}]} + $x')"
}
# api METHOD PATH [JSON]: admin call with the master key
api() { curl -s -X "$1" "$GW$2" -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' ${3:+-d "$3"}; }
hdr() { grep -i "^$1:" "$HDR" | head -1 | cut -d' ' -f2- | tr -d '\r'; }
pass() { echo "PASS  $*"; exit 0; }
fail() { echo "FAIL  $*"; exit 1; }
EOF

export GW=http://192.168.1.101:4000
read -rsp 'Master key: ' MK; echo; export MK
echo "master key ****${MK: -4}"

Notes & gotchas

Warning: Check the version against the LiteLLM security advisories. After the March 2026 PyPI incident, treat any LiteLLM installed with an unpinned pip install litellm in that window as suspect, and rotate any keys that host held. A floating image tag such as main-stable or main-latest isn't compromised by itself, but you can't tell which build you'll get on the next pull. Record the digest from step 2; Lab 3 pins it.

  • A master key in the config (general_settings.master_key) or env (LITELLM_MASTER_KEY) must start with sk-.

  • Don't open /health (without /liveliness) yet. It sends a real request to every model, which costs tokens and makes LM Studio or Ollama load each local model in turn.

Lab 2: Supporting Services on .100: Postgres & Redis

192.168.1.100, tested from 192.168.1.101

Goalrun Postgres 16 and Redis 7 on .100 with pinned tags, persistent volumes and generated passwords, published on 0.0.0.0 and reachable from .101.

1. Check Docker and the ports

ssh "$USER"@192.168.1.100   # your login on .100
docker version --format 'engine {{.Server.Version}}'; docker compose version
sudo ss -ltnp | grep -E ':(5432|6379|3000|9999)\b'      # should print nothing

2. Write the .env and compose file

mkdir -p ~/litellm-lab && cd ~/litellm-lab
umask 077
cat > .env <<EOF
POSTGRES_PASSWORD=$(openssl rand -hex 24)
REDIS_PASSWORD=$(openssl rand -hex 24)
EOF

cat > docker-compose.yml <<'EOF'
name: litellm-lab
services:
  postgres:
    image: docker.io/library/postgres:16.15
    restart: unless-stopped
    environment:
      POSTGRES_USER: litellm
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: litellm
    ports: ["0.0.0.0:5432:5432"]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U litellm -d litellm"]
      interval: 10s
      retries: 5

  redis:
    image: docker.io/library/redis:7.4.11
    restart: unless-stopped
    user: redis
    environment:
      REDIS_PASSWORD: ${REDIS_PASSWORD}
    command: ["sh", "-c", "exec redis-server --requirepass \"$$REDIS_PASSWORD\" --appendonly yes"]
    ports: ["0.0.0.0:6379:6379"]
    volumes: [redisdata:/data]
    healthcheck:
      test: ["CMD-SHELL", "redis-cli -a \"$$REDIS_PASSWORD\" --no-auth-warning ping | grep -q PONG"]
      interval: 10s
      retries: 5

volumes:
  pgdata:
  redisdata:
EOF

3. Start and check

docker compose up -d
docker compose ps                                      # both "healthy" after ~10 s
sudo ss -ltn | grep -E '0.0.0.0:(5432|6379)'

Verify from .101

Test from the gateway host the same way LiteLLM will connect: from a container on .101, by IP, with the password.

ssh "$USER"@192.168.1.101   # your login on .101
for p in 5432 6379; do timeout 3 bash -c "</dev/tcp/192.168.1.100/$p" && echo "$p open" || echo "$p CLOSED"; done

read -rsp 'Redis password (from .100 ~/litellm-lab/.env): ' RP; echo
sudo podman run --rm -e RP="$RP" docker.io/library/redis:7.4.11 \
  sh -c 'redis-cli -h 192.168.1.100 -a "$RP" --no-auth-warning ping'          # PONG
sudo podman run --rm docker.io/library/postgres:16.15 pg_isready -h 192.168.1.100 -U litellm
unset RP

Notes & gotchas

  • Skip Postgres if Lab 1 showed "db": "connected". Pointing LiteLLM at a new, empty database starts you over with no keys, teams or spend history. Delete the postgres service from the file in that case.
  • Ports published by Docker usually bypass firewalld, because Docker inserts its own forwarding rules. If the /dev/tcp test says CLOSED anyway, open them: sudo firewall-cmd --permanent --add-port={5432,6379,3000,9999}/tcp && sudo firewall-cmd --reload.
  • $$REDIS_PASSWORD is deliberate: Compose turns $$ into a literal $, so the shell inside the container expands it and the password never appears in docker inspect's command line.
  • The tags were current when this was written. Moving to a newer patch (16.x, 7.4.x) is safe; moving Postgres to a new major version is not, because the data directory format changes.
  • Use openssl rand -hex rather than -base64. Base64 output can contain / and +, which break the DATABASE_URL in Lab 3 unless URL-encoded.
  • Redis is published with a password but no TLS, which is fine on an isolated lab LAN. For anything else, bind it to the one interface .101 uses and add a firewall rule allowing only 192.168.1.101.

4. Write the guardrail

LiteLLM loads guard.SSNGuard from guard.py in the same directory as the config file. Lab 8 explains how it works.

sudo tee $D/guard.py >/dev/null <<'EOF'
import re

from fastapi import HTTPException
from litellm.integrations.custom_guardrail import CustomGuardrail

SSN = re.compile(r"\b\d{3}-\d{2}-\d{4}\b")


def _texts(data):
    # every user-supplied string in a chat, messages or responses request
    for msg in data.get("messages") or []:
        content = msg.get("content")
        if isinstance(content, str):
            yield content
        elif isinstance(content, list):
            for part in content:
                if isinstance(part, dict) and isinstance(part.get("text"), str):
                    yield part["text"]
    if isinstance(data.get("input"), str):
        yield data["input"]


class SSNGuard(CustomGuardrail):
    async def async_pre_call_hook(self, user_api_key_dict, cache, data, call_type):
        if any(SSN.search(t) for t in _texts(data)):
            raise HTTPException(
                status_code=400,
                detail={"error": "Blocked by ssn-guard: the prompt contains a US Social Security number."},
            )
        return data
EOF
sudo chmod 644 $D/guard.py

6. Recreate LiteLLM on a pinned image

Env-file changes and new mounts only take effect in a new container, so restart isn't enough. Save the run command as a script so it's the single source of truth from now on. Paste the digest from Lab 1 into IMG, and list every network Lab 1 showed in NETS.

sudo tee $D/run-litellm.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# Recreates the LiteLLM container. Rerun after editing litellm.env or upgrading IMG.
set -euo pipefail
IMG="ghcr.io/berriai/litellm@sha256:<digest-from-lab-1>"
NETS="--network podman"     # e.g. "--network docker_default --network podman" if the DB is a container
D=/opt/litellm
podman rm -f litellm 2>/dev/null || true
podman run -d --name litellm --restart=always $NETS \
  --env-file $D/litellm.env \
  -v $D/config.yaml:/app/config.yaml:ro,Z \
  -v $D/guard.py:/app/guard.py:ro,Z \
  -p 4000:4000 \
  "$IMG" --config /app/config.yaml --port 4000
EOF
sudo chmod 700 $D/run-litellm.sh
sudo $D/run-litellm.sh
sudo podman logs -f litellm 2>&1 | grep -m1 -E 'Uvicorn running|Error|Traceback'

Notes & gotchas

Warning: A YAML file may contain each top-level key only once. If you paste a second litellm_settings: under the first, the parser silently keeps only the last one and your earlier settings vanish. Merge into the existing block instead.

  • Rollback is in Appendix B: copy the .bak-$TS files back and rerun the script.
  • cache: true caches every model, including any you already had. To make caching opt-in, add mode: default_off under cache_params; requests then opt in with "cache": {"use-cache": true}.
  • If you already had fallbacks:, add - gpt-mini: ["claude-fast"] as another list item. Don't start a second fallbacks: key.
  • If the existing config has a literal master_key: sk-..., you can leave it. Moving it into the env file keeps it out of config.yaml and its backups.
  • No cloud keys? Point the aliases at a local OpenAI-compatible server instead, e.g. model: openai/<local-model> plus api_base: os.environ/LMSTUDIO_API_BASE. Labs 4–8 work the same, though Lab 5's fallback then goes from one local model to another.
  • :Z relabels the mounted files for SELinux (Rocky/RHEL). Without it the container gets "permission denied" reading guard.py.
  • Single-file bind mounts follow the inode. Some editors save by writing a new file, so the running container keeps reading the old one. Recreating with the script (or podman restart) picks up the new file.
  • Startup errors to look for: Could not import SSNGuard from guard (missing mount or typo), ConnectionError ... 6379 (Redis password or firewall), P1001 (Prisma can't reach Postgres).
