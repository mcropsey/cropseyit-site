LiteLLM Gateway Labs: Chat & Agents

Hands-on labs for sending every chat and every AI agent in a home lab through one LiteLLM gateway: one address, one key per app, and one log of who asked what.

You'll start with plain chat requests, put a chat web UI in front of the gateway, then build five agents: a single tool-using agent, agents running as always-on services, agents published through the gateway over A2A, an agent whose tools come from an MCP server, and a coordinator that hands work to the other agents. Lab 10 then points a coding agent at the gateway too.

Nothing talks to the model server directly. The chat UI, the agents and the coding agent all send their requests to the gateway, and the gateway checks the key and forwards the request to the model. That's what lets you swap models, limit an app, or see what an agent did, in one place.

Podman and Quadlet

Every container in these labs runs under rootful Podman (sudo podman); there's no Docker anywhere. A container started with plain podman run stops when the host reboots and stays stopped, because there's no always-running daemon to bring it back, as there is with Docker. So every lab uses Quadlet instead: you write a small .container file in /etc/containers/systemd/, and Podman turns it into a normal systemd service. systemctl start, status, restart and journalctl all work, and it starts at boot. This is the Red Hat-recommended way on Podman 4.4 and newer (Rocky 9 and 10 have Podman 5).

A Quadlet file has three sections: [Unit] (a description and what it depends on), [Container] (everything you'd otherwise type after podman run: image, ports, volumes, environment), and [Service]/[Install] (systemd's restart policy and "start at boot"). After adding or changing one, run sudo systemctl daemon-reload so systemd regenerates the service. You don't run systemctl enable on Quadlet services; the [Install] section takes care of that.

Before you start

  • A gateway host: a Rocky Linux 9 or 10 server (RHEL works too) with sudo, internet access to pull images, and at least 2 GB of RAM (4 GB if it's your lab host too). Nothing needs to be installed on it first: Lab 0 installs Podman, LiteLLM and Postgres, and works with SELinux enforcing and firewalld running, as Rocky ships.
  • A lab host: any Rocky Linux machine with sudo that the gateway can reach over the network. Lab 1 installs what it needs. It can be the gateway host itself: see One machine.
  • SSH with sudo from the lab host to the gateway host, to read the master key. Not needed on one machine.
  • A model that can call tools. These labs use qwen/qwen3.8-27b in LM Studio. In LM Studio, set its default context length to at least 32k (gear icon on the model, then Context Length). LM Studio loads models on demand with that setting, and a small default leaves a "thinking" model no room to answer.
  • The labs were tested with LiteLLM v1.104.0, Podman 5.8, Python 3.12, openai 3.24, mcp 2.3 and a2a-sdk 1.2.

How to read the commands

The labs are mostly shell commands, and the same handful of tools comes up again and again. Each command block has a What these commands do box under it that goes through it line by line. This section explains the tools once, so the boxes can stay short.

Shell basics the labs rely on

  • Variables. export GW=http://... stores a value; $GW uses it. The labs keep the gateway address in $GW and keys in variables like $MK, so you never paste a key into a command. Variables only last as long as the shell, so Lab 1 puts them in a setup file, and every lab starts with . ~/gw-labs/env.sh to set them again (Lab 1, step 3). Every key you create is saved in ~/gw-labs/keys.env, which that file loads too.
  • Reading a secret. read -rsp 'Prompt: ' MK asks you to paste a value and stores it in MK. -s hides what you type, -p shows the prompt, -r keeps backslashes as they are. The echo after it just moves to a new line, since the hidden input doesn't.
  • $(...) runs the command inside and drops its output in place. $(date +%F) becomes today's date, such as 2026-10-06, which the labs use to name backup files.
  • Quotes. Inside 'single quotes' the shell changes nothing, which is why JSON is written that way. Inside "double quotes" it still replaces $VARIABLES, which is why the Authorization header uses them.
  • Long lines. A \ at the end of a line means the command carries on to the next line. | sends one command's output into the next, as in curl ... | jq.
  • Grey text after # is a comment. The shell ignores it, so you can paste whole blocks. Comment lines that show output tell you what to expect, not what to type.

A typical gateway call, taken apart:

curl -s $GW/v1/models -H "Authorization: Bearer $MK" | jq -r '.data[].id'

What these commands do

curl -s $GW/v1/models
Send a GET request to /v1/models on the gateway, without the progress bar.
-H "Authorization: Bearer $MK"
Prove who you are. Every gateway call except the health checks needs a key in this header; $MK is replaced with your key before curl runs.
| jq -r '.data[].id'
The answer is {"data": [{"id": "qwen3.8-27b", ...}, ...]}. This goes into data, takes each item's id, and prints them one per line.

Calls that send data add -H 'Content-Type: application/json', which tells the gateway the body is JSON, and -d with the body. When the body contains a key or ID from a variable, the labs first write it to a small .json file with an unquoted heredoc and then send it with -d @file. You can cat the file to see exactly what's being sent.

Part 1: Podman, SELinux and the model server

Rocky Linux and RHEL ship Podman in the base repositories. Quadlet, the feature that turns container files into systemd services (see the overview), is built into Podman 4.4 and newer.

cat /etc/rocky-release                     # Rocky Linux release 9.x or 10.x
sudo dnf -y install podman jq openssl
podman --version                           # 5.x on Rocky 9.6+ and 10
ls /usr/libexec/podman/quadlet             # present = Quadlet is available
getenforce                                 # Enforcing: leave it that way
curl -s http://192.168.1.194:1234/v1/models | jq -r '.data[].id'   # your model server: lists qwen/qwen3.8-27b

What these commands do

cat /etc/rocky-release
Show which release you're on. The labs were tested on Rocky 9.8 and 10.2.
sudo dnf -y install podman jq openssl
Install Podman (runs containers), jq (reads JSON, see How to read the commands) and openssl (generates the random passwords in Part 2). Podman pulls in container-selinux, the SELinux policy for containers. -y answers yes to the confirmation prompt.
podman --version
Check the version. Quadlet needs 4.4 or newer.
ls /usr/libexec/podman/quadlet
Quadlet is a small program shipped with Podman that systemd runs at boot and on daemon-reload. If ls finds it, you have it.
getenforce
Show the SELinux mode. Rocky ships with Enforcing, and this lab works that way; don't turn it off.
curl -s http://192.168.1.194:1234/v1/models | jq ...
Ask the model server, from the gateway host, which models it has. If this prints nothing, fix that first (is LM Studio's server running and set to serve on the network, not just localhost?): the gateway can't work without it.

SELinux and the firewall. Both stay on. SELinux needs only one thing from you: the :Z on the one file mounted from the host (config.yaml, in Part 2), which relabels it so the container may read it. Named volumes such as the database's are labelled by Podman automatically, and containers may connect out to the model server without any change. firewalld blocks port 4000 until you open it in Part 2. If a container ever logs "permission denied" on a file, sudo ausearch -m avc -ts recent shows what SELinux blocked.

Everything here runs as root (sudo podman). Root containers and their Quadlet files live in /etc/containers/systemd/; rootless ones would live in ~/.config/containers/systemd/ and need loginctl enable-linger to start at boot, which is why these labs stick to rootful.

Part 2: Install LiteLLM and Postgres

The result is two Quadlet services: litellm-db (Postgres, which stores virtual keys, agents and spend logs) and litellm (the gateway), joined by a private network so the database is never exposed on the LAN.

Secrets. Two env files, readable by root only. Podman reads them when it creates each container, so no secret appears in a config file or in ps output. The master key must start with sk-.

sudo mkdir -p /opt/litellm
sudo touch /opt/litellm/db.env /opt/litellm/litellm.env
sudo chmod 600 /opt/litellm/db.env /opt/litellm/litellm.env

DBPASS=$(openssl rand -hex 24)
read -rsp 'Admin UI password: ' UIPASS; echo

sudo tee /opt/litellm/db.env >/dev/null <<EOF
POSTGRES_USER=litellm
POSTGRES_PASSWORD=$DBPASS
POSTGRES_DB=litellm
EOF

sudo tee /opt/litellm/litellm.env >/dev/null <<EOF

sudo grep '^LITELLM_MASTER_KEY=' /opt/litellm/litellm.env   # your master key: save it in a password manager

Run that block once. Running it again writes a new database password, but Postgres keeps the old one from its first start, so LiteLLM can no longer log in. To start over completely, see Starting over below.

Config. model_list is the list of models the gateway serves. model_name is the name clients ask for; model is the real model, where the openai/ prefix means "talk to this server with the OpenAI API", which LM Studio speaks. os.environ/NAME tells LiteLLM to read a value from the environment. Add one entry per model you want to serve.

sudo tee /opt/litellm/config.yaml >/dev/null <<'EOF'
model_list:
  - model_name: qwen3.8-27b
    litellm_params:
      model: openai/qwen/qwen3.8-27b       # the model's id in LM Studio
      api_base: os.environ/LMSTUDIO_API_BASE
      api_key: not-needed                  # LM Studio doesn't check keys

litellm_settings:
  drop_params: true          # ignore request options the model server doesn't support
  request_timeout: 600       # local models can be slow on long prompts

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL
  store_model_in_db: true    # reload agents and other API-added objects from the database at every start
EOF

What these commands do

sudo tee /opt/litellm/config.yaml >/dev/null <<'EOF'
Write the YAML below into config.yaml. The heredoc is quoted, so os.environ/... lines are saved as typed; LiteLLM looks those values up in the env file when it starts. The secrets stay out of this file, so it's safe to show people.

Two quality-of-life settings: silently drop request options LM Studio doesn't support instead of failing, and wait up to 10 minutes for slow local models.

Without it, every restart or reboot empties the gateway's agent list, although the rows are still in the database. It also lets you add models from the admin UI.

Quadlet files. A network, a volume for the database files, and one .container file per container. Requires= and After= start the database first, and Notify=healthy makes systemd wait until Postgres actually answers before it starts LiteLLM.

sudo tee /etc/containers/systemd/litellm-db.volume >/dev/null <<'EOF'

What these commands do

litellm.network
A private container network called litellm. Containers on it reach each other by container name, which is why DATABASE_URL can say litellm-db. Nothing outside the host can reach the database.
litellm-db.volume
A named volume: storage that Podman manages and that outlives the container, so the database survives restarts and upgrades.
Image=
Which image to run, with a pinned version tag. Podman downloads it on the first start.
Network= / Volume=
Join the network and mount the volume above. Quadlet files refer to each other by file name (litellm.network).
EnvironmentFile=
Load the variables from the env file you made, so secrets don't appear in this file.
HealthCmd= / Notify=healthy
Every 10 seconds, run pg_isready inside the container to check Postgres answers. Notify=healthy tells systemd the service has only started once that check passes.
Requires= / After=
LiteLLM needs the database: start litellm-db first, and wait for it.
PublishPort=4000:4000
Make port 4000 inside the container reachable on port 4000 of the host (host:container).
Volume=/opt/litellm/config.yaml:/app/config.yaml:ro,Z
Show the host's config file inside the container at /app/config.yaml, read-only (ro). Z relabels it for SELinux so the container is allowed to read it.
Exec=
Arguments passed to the program in the image: which config to use and which port to listen on.
Restart= / RestartSec= / TimeoutStartSec=
Restart it whenever it stops, 10 seconds apart, and allow 5 minutes for the first start, which downloads the image.
WantedBy=multi-user.target
Start it at boot.

sudo systemctl start litellm

sudo journalctl -u litellm -f

Part 3: Upgrades and backups

Which change needs what.

You changedRun
config.yaml or litellm.envsudo systemctl restart litellm (a Quadlet restart creates a fresh container, so env file changes are picked up)
A .container, .network or .volume filesudo systemctl daemon-reload, then restart the service
Keys, agents, MCP servers (through the API or UI)Nothing; they're stored in the database. The gateway caches keys, so a change to a key that was used recently can take up to a minute to apply. Blocking a key applies at once.

Back up the database before every upgrade, and on a schedule if the spend logs matter to you:

sudo podman exec litellm-db pg_dump -U litellm litellm | sudo tee /opt/litellm/backup-$(date +%F).sql >/dev/null
sudo chmod 600 /opt/litellm/backup-*.sql

What these commands do

podman exec litellm-db pg_dump -U litellm litellm
Dump the whole database as SQL, from inside its container.
| sudo tee /opt/litellm/backup-$(date +%F).sql
Save it to a file named with today's date. To restore, feed the file back in: sudo cat FILE | sudo podman exec -i litellm-db psql -U litellm -d litellm, into an empty database.

Upgrade LiteLLM by changing the image tag. Read the release notes for the versions you're skipping first; LiteLLM runs its own database migrations at startup.

sudo sed -i 's#^Image=ghcr.io/berriai/litellm:.*#Image=ghcr.io/berriai/litellm:v1.105.0#' /etc/containers/systemd/litellm.container

What these commands do

sudo sed -i 's#^Image=ghcr.io/berriai/litellm:.*#...:v1.105.0#' ...
Edit the Quadlet file in place: replace the whole Image= line, whatever tag it has now (.* matches the rest of the line), with the new pinned version. Opening it in vi and changing the line does the same.
grep ^Image= ...

Regenerate the service from the changed file, then restart it. The new container uses the new image, which Podman downloads first.
curl ... /openapi.json | jq -r .info.version
The gateway describes its own API at /openapi.json, including its version number. This prints just the version.
  • Pin the version. A floating tag such as main-stable or latest means you can't tell which build you run, and a pull can silently change it. On 24 March 2026, LiteLLM versions 1.82.7 and 1.82.8 on PyPI carried credential-stealing code for a few hours before they were removed, so know exactly what you run. For full reproducibility, pin the digest: Image=ghcr.io/berriai/litellm@sha256:... (sudo podman image inspect --format '{{index .RepoDigests 0}}' <image> prints it).
  • LITELLM_SALT_KEY in litellm.env encrypts provider keys stored through the UI. Keep a copy of litellm.env with your database backups, and never change the salt key, or LiteLLM can't decrypt them.
  • Cloud models go in model_list the same way: model: anthropic/claude-haiku-4-5-20251001 with api_key: os.environ/ANTHROPIC_API_KEY, or model: openai/gpt-4.1-mini with api_key: os.environ/OPENAI_API_KEY, and the key itself in litellm.env.

  -H "Authorization: Bearer $MK" \

  -d '{
        "model": "qwen3.8-27b",

What these commands do

curl -s $GW/v1/chat/completions
Send the request to /v1/chat/completions, the OpenAI chat API. LiteLLM speaks it whatever provider is behind the model name, so any OpenAI-compatible app or library can use the gateway.
-H "Authorization: Bearer $MK"
The key. The master key works for now; Lab 3 gives each app its own key.
-H 'Content-Type: application/json'
Tell the gateway the body is JSON.
-d '{...}'
The body. Sending one makes this a POST request. The single quotes keep the shell away from the JSON's own double quotes.
"model": "qwen3.8-27b"
Which model to use: the one these labs use (Lab 1).
"messages": [...]
The conversation. The system message sets the behaviour; user messages are what you type.
| jq
Pretty-print the whole response.

2. The API has no memory

Ask a follow-up question on its own and the model has no idea what you mean:

curl -s $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "qwen3.8-27b", "messages": [{"role": "user", "content": "What did I just ask you?"}]}' \
  | jq -r '.choices[0].message.content'

What these commands do

-d '{"model": ..., "messages": [...]}'
The same request as before, squeezed onto one line, with no system message and one question.
jq -r '.choices[0].message.content'
Print only the reply text, as plain text.

Every chat app, including ChatGPT-style web UIs, keeps the conversation itself and sends the whole history with every request, adding the model's earlier answers as assistant messages:

curl -s $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "qwen3.8-27b", "messages": [
        {"role": "user",      "content": "My favourite distro is Rocky Linux."},
        {"role": "assistant", "content": "Nice choice!"},
        {"role": "user",      "content": "What is my favourite distro?"}
      ]}' | jq -r '.choices[0].message.content'

What these commands do

{"role": "assistant", ...}
A message the model "said" earlier. You write it yourself here, the way a chat app replays the history. The model treats the three messages as the conversation so far and answers the last one.

That's also why long conversations get slower and more expensive: every turn re-sends everything before it.

3. Streaming

With "stream": true, the gateway sends the answer in small pieces as the model produces them, the way chat UIs show text appearing word by word. curl -N turns off buffering so you see them arrive:

curl -sN $GW/v1/chat/completions -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' \
  -d '{"model": "qwen3.8-27b", "stream": true, "messages": [{"role": "user", "content": "Count from 1 to 5."}]}'
# data: {"choices":[{"delta":{"content":"1"}...}]}
# data: {"choices":[{"delta":{"content":","}...}]}
# ...
# data: [DONE]

What these commands do

curl -sN
-N prints each piece the moment it arrives instead of collecting the whole answer first.
"stream": true
Ask for a streamed answer: a series of data: lines, each holding a few characters in delta.content, ending with data: [DONE]. No jq here, because the output isn't a single JSON document.

chat.py keeps the history in a list (step 2) and streams each answer (step 3):

cat > ~/gw-labs/chat.py <<'EOF'
"""chat.py: a terminal chat client. Every message goes through the LiteLLM gateway."""
import os

from openai import OpenAI

client = OpenAI(base_url=os.environ["GW"] + "/v1", api_key=os.environ["KEY"])
MODEL = os.environ.get("MODEL", "qwen3.8-27b")

# The API has no memory. The conversation lives in this list, and the
# whole list is sent with every request.
history = [{"role": "system", "content": "You are a helpful assistant. Keep answers short."}]

print(f"Chatting with {MODEL} through {os.environ['GW']}. Ctrl-D to quit.")
while True:
    try:
        question = input("\nyou> ").strip()
    except EOFError:
        break
    if not question:
        continue
    history.append({"role": "user", "content": question})

    stream = client.chat.completions.create(model=MODEL, messages=history, stream=True)
    print("ai > ", end="", flush=True)
    answer = ""
    for chunk in stream:                       # print each piece as it arrives
        piece = chunk.choices[0].delta.content if chunk.choices else None
        if not piece:
            continue
        answer += piece
        print(piece, end="", flush=True)
    print()
    history.append({"role": "assistant", "content": answer})
EOF

What these commands do

cat > ~/gw-labs/chat.py <<'EOF'
cat > writes everything between this line and the final EOF line into ~/gw-labs/chat.py. The quotes around 'EOF' save the program exactly as typed, so the shell doesn't touch any $ in it. Paste the whole block at once, or open the file in an editor and paste just the program.

What these commands do

client = OpenAI(base_url=..., api_key=...)
A client for the OpenAI API, pointed at the gateway ($GW/v1) instead of OpenAI, with the key from KEY. This line is the only thing that makes it a "gateway" program.
MODEL = os.environ.get("MODEL", "qwen3.8-27b")
Use the model named in MODEL, or qwen3.8-27b if it isn't set.
history = [{"role": "system", ...}]
The conversation so far, starting with the system message. This list is the program's memory (step 2).
input("\nyou> ")
Wait for you to type a line. Ctrl-D raises EOFError, which ends the loop.
history.append({"role": "user", ...})
Add your question to the conversation.
client.chat.completions.create(..., messages=history, stream=True)
Send the whole history and ask for a streamed answer (step 3).
for chunk in stream: ... print(piece, end="", flush=True)
Print each piece as it arrives, without a newline, and collect the pieces into answer.
history.append({"role": "assistant", "content": answer})
Add the full answer to the conversation, so the next question can refer to it.
KEY=$MK python chat.py
# you> My name is Pat.
# ai > Hi Pat! How can I help you today?
# you> What is my name?
# ai > Your name is Pat.

What these commands do

KEY=$MK python chat.py
Run the program with the variable KEY set to your master key, for this one command only. chat.py reads the key and the gateway address ($GW) from the environment rather than having them written into the code. Ctrl-D quits.

Notes

  • Change the model per run with MODEL=<another model> KEY=$MK python chat.py. The program doesn't know or care which real model answers.
  • The admin UI at http://192.168.1.104:4000/ui (login: Lab 1, Notes) has a Playground page that does the same thing in the browser.
  • If a request hangs for a minute and then answers, LM Studio was loading the model. The first request after a model unloads is always slow.

Why

The master key can do everything, including creating and deleting keys. Every app and agent in these labs gets its own virtual key instead. A virtual key can be limited to certain models, a request rate, a budget, and (Labs 7–9) certain agents and tools. Every request is logged under the key's name, and you can revoke one key without touching the others.

1. Create a key for the chat UI

touch ~/gw-labs/keys.env && chmod 600 ~/gw-labs/keys.env

What these commands do

touch ... && chmod 600 ...
Create ~/gw-labs/keys.env if it doesn't exist, and make it readable and writable by you only (600), before any key goes in.
curl -s $GW/key/delete ... >/dev/null
Delete any key already named chat-ui. Aliases must be unique, so without this, running the block a second time fails. On the first run there's nothing to delete; >/dev/null hides that reply.
UIKEY=$(curl -s $GW/key/generate ...)
Ask the gateway to create a new virtual key, and store it in UIKEY ($(...) captures the output). Only the master key may create keys. Labs 4 and 7 use UIKEY too.
"key_alias": "chat-ui"
The key's name, which you'll see in logs and in the UI.
"models": [...]
The allow-list: the only models this key may use. Leave it out and the key can use every model.
"rpm_limit": 60
Requests per minute. Request number 61 inside a minute gets HTTP 429.
jq -r '.key // empty'
Take just the key from the response. If the request failed there is no key, and // empty gives nothing instead of the word null.
[ -n "$UIKEY" ] && sed -i ... && echo ... >> keys.env
Only if a key came back (-n: not empty), delete any old UIKEY= line from the file and add the new one. The key is filled in from the variable, so it never appears in your shell history.
echo ${UIKEY:0:6}
Print the first six characters, sk-.... Blank means no key was made, usually because $MK isn't set (see New shell?). To see the gateway's error, run the generate curl on its own, without | jq ....

LiteLLM stores only a hash of the key, so it can never show it to you again: keys.env is your copy. Running the block again replaces the key, and anything holding the old one (Open WebUI in Lab 4, the agents in Lab 6) then needs the new one.

Tip: env.sh (Lab 1) loads keys.env in every new shell, so UIKEY and every key you save in later labs come back by themselves.

4. Two shortcuts for the labs ahead

Every lab from here on makes a key, and several read the gateway's request log. Those commands are long, so save them as two shell functions: a short name for a group of commands. newkey does exactly what step 1 did, and gwlogs fetches the log.

cat > ~/gw-labs/helpers.sh <<'EOF'
# Shortcuts for the LiteLLM labs. env.sh loads this file.

# newkey VAR ALIAS '{settings}': replace the key called ALIAS and save it in keys.env as VAR
newkey() {
  local resp key
  jq -n --arg a "$2" '{key_aliases: [$a]}' \
    | curl -s $GW/key/delete -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' -d @- >/dev/null
  resp=$(printf '%s' "${3:-$(cat)}" | jq --arg a "$2" '. + {key_alias: $a}' \
    | curl -s $GW/key/generate -H "Authorization: Bearer $MK" -H 'Content-Type: application/json' -d @-)
  key=$(printf '%s' "$resp" | jq -r '.key // empty')
  [ -n "$key" ] || { echo "newkey: no key made for $2: $resp" >&2; return 1; }
  sed -i "/^$1=/d" ~/gw-labs/keys.env && echo "$1=$key" >> ~/gw-labs/keys.env
  export "$1=$key"
  echo "$1=${key:0:6}... saved in keys.env"
}

# gwlogs [DAYS]: every request the gateway logged today, or over the last DAYS days
gwlogs() {
  curl -s "$GW/spend/logs?start_date=$(date -u -d "${1:-0} days ago" +%F)&end_date=$(date -u -d tomorrow +%F)&summarize=false" \
    -H "Authorization: Bearer $MK"
}
EOF
. ~/gw-labs/env.sh
gwlogs | jq -r '.[] | select(.metadata.user_api_key_alias == "chat-ui") | "\(.startTime)  \(.model_group)"'

What makes it an agent

A chat model only produces text. An agent is a loop around the model that lets it do things:

  1. You send the question, plus a description of each tool: its name, what it does, and its parameters as JSON Schema.
  2. Instead of answering, the model can reply with a tool call: "run check_port with host=192.168.1.104, port=22".
  3. Your code runs that function and sends the result back as a tool message.
  4. Repeat until the model replies with plain text. That's the answer.

The model never runs anything itself; your code decides which functions exist and runs them. Every step of the loop is an ordinary chat request through the gateway.

"""ops-agent: a small tool-using agent. Every model call goes through the LiteLLM gateway."""
import json
import os
import socket
import sys
import time
from datetime import datetime, timezone

import httpx
from openai import OpenAI

client = OpenAI(base_url=os.environ["GW"] + "/v1", api_key=os.environ["AGENT_KEY"])
MODEL = os.environ.get("AGENT_MODEL", "qwen3.8-27b")


# ---- the tools: plain Python functions -------------------------------------
def get_time() -> str:
    return datetime.now(timezone.utc).isoformat(timespec="seconds")


def check_url(url: str) -> str:
    start = time.monotonic()
    try:
        r = httpx.get(url, timeout=5, follow_redirects=True)
        return f"HTTP {r.status_code} in {(time.monotonic() - start) * 1000:.0f} ms"
    except httpx.HTTPError as err:
        return f"failed: {err!r}"


def check_port(host: str, port: int) -> str:
    try:
        with socket.create_connection((host, int(port)), timeout=3):
            return f"{host}:{port} is open"
    except OSError as err:
        return f"{host}:{port} is closed or unreachable ({err})"


TOOLS = {"get_time": get_time, "check_url": check_url, "check_port": check_port}


def call_tool(name: str, arguments: str) -> str:
    """Run one tool the model asked for. Mistakes go back to the model as text, so it can retry."""
    if name not in TOOLS:
        return f"error: there is no tool called {name!r}"
    try:
        return TOOLS[name](**json.loads(arguments or "{}"))
    except (json.JSONDecodeError, TypeError) as err:
        return f"error: bad arguments for {name}: {err}"


# ---- how the model learns about the tools: JSON Schema descriptions --------
TOOL_SPECS = [
    {"type": "function", "function": {
        "name": "get_time", "description": "Current date and time in UTC.",
        "parameters": {"type": "object", "properties": {}}}},
    {"type": "function", "function": {
        "name": "check_url", "description": "Fetch a URL and report the HTTP status and response time.",
        "parameters": {"type": "object", "properties": {"url": {"type": "string"}}, "required": ["url"]}}},
    {"type": "function", "function": {
        "name": "check_port", "description": "Test whether a TCP port on a host accepts connections.",
        "parameters": {"type": "object", "properties": {"host": {"type": "string"}, "port": {"type": "integer"}},
                       "required": ["host", "port"]}}},
]

# A2A services (Lab 6) reuse this file and override these two settings per agent.
SYSTEM = os.environ.get("AGENT_PROMPT", "You are ops-agent, a home-lab operations assistant. "
                        "Use the tools to check facts instead of guessing. Answer briefly.")
USE_TOOLS = os.environ.get("AGENT_TOOLS", "on") == "on"


# ---- the agent loop ---------------------------------------------------------
def run(question: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}]
    for _ in range(max_steps):
        extra = {"tools": TOOL_SPECS} if USE_TOOLS else {}
        reply = client.chat.completions.create(model=MODEL, messages=messages, **extra)
        msg = reply.choices[0].message
        if not msg.tool_calls:                      # no tool requested: this is the answer
            return msg.content
        messages.append(msg.model_dump(exclude_none=True))
        for call in msg.tool_calls:                 # run each requested tool, return the result
            result = call_tool(call.function.name, call.function.arguments)
            print(f"  [tool] {call.function.name}({call.function.arguments}) -> {result}", file=sys.stderr)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return "Stopped: too many steps."


if __name__ == "__main__":
    print(run(" ".join(sys.argv[1:]) or "Is the gateway at 192.168.1.104 port 4000 up, and what time is it?"))
EOF

A2A in one paragraph

A script is only useful to the person running it. To let other programs and other agents use an agent, it needs a network interface. A2A (Agent2Agent) is an open protocol for that. An A2A agent publishes an agent card, a JSON description of who it is and what it can do, at /.well-known/agent-card.json, and accepts messages as JSON-RPC SendMessage calls over HTTP. LiteLLM understands A2A, which is what Lab 7 uses.

Up to now, every call went from your lab host to the gateway. From here on, calls also go the other way: in Lab 7 the gateway forwards agent calls to the agents you start here, and in Lab 8 it fetches tools from an MCP server on the lab host. For that, the gateway needs an address for your lab host that it can reach. localhost won't do: on the gateway, localhost is the gateway itself. """Serve the agent from agent.py over A2A (Agent2Agent), so other agents can call it."""
import asyncio
import os

import uvicorn
from a2a.helpers import get_message_text, new_task_from_user_message, new_text_message, new_text_part
from a2a.server.agent_execution import AgentExecutor, RequestContext
from a2a.server.events import EventQueue
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.routes import create_agent_card_routes, create_jsonrpc_routes
from a2a.server.tasks import InMemoryTaskStore, TaskUpdater
from a2a.types import AgentCapabilities, AgentCard, AgentInterface, AgentSkill, TaskState
from starlette.applications import Starlette

import agent  # the Lab 5 agent: agent.run(question) -> answer

NAME = os.environ.get("AGENT_NAME", "ops-agent")
DESCRIPTION = os.environ.get("AGENT_DESCRIPTION", "Checks home-lab hosts, ports and URLs.")
PORT = int(os.environ.get("PORT", "8601"))
PUBLIC_URL = os.environ["PUBLIC_URL"]  # how other hosts reach this agent: http://<lab host>:8601


class Executor(AgentExecutor):
    async def execute(self, context: RequestContext, event_queue: EventQueue) -> None:
        task = context.current_task or new_task_from_user_message(context.message)
        if not context.current_task:
            await event_queue.enqueue_event(task)
        updater = TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id)
        await updater.update_status(state=TaskState.TASK_STATE_WORKING, message=new_text_message("Working..."))

        answer = await asyncio.to_thread(agent.run, get_message_text(context.message) or "")

        await updater.add_artifact(parts=[new_text_part(text=answer, media_type="text/plain")])
        await updater.update_status(state=TaskState.TASK_STATE_COMPLETED, message=new_text_message(answer))

    async def cancel(self, context: RequestContext, event_queue: EventQueue) -> None:
        raise NotImplementedError


card = AgentCard(
    name=NAME,
    description=DESCRIPTION,
    version="1.0.0",
    default_input_modes=["text/plain"],
    default_output_modes=["text/plain"],
    capabilities=AgentCapabilities(streaming=False),
    supported_interfaces=[AgentInterface(protocol_binding="JSONRPC", url=PUBLIC_URL, protocol_version="1.0")],
    skills=[AgentSkill(id=NAME, name=NAME, description=DESCRIPTION, tags=["lab"])],
)
handler = DefaultRequestHandler(agent_executor=Executor(), task_store=InMemoryTaskStore(), agent_card=card)
app = Starlette(routes=[*create_agent_card_routes(card), *create_jsonrpc_routes(handler, "/")])

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=PORT)

1. The MCP server

The mcp library turns plain Python functions into MCP tools; the docstring becomes the tool description the model reads.

"""lab-tools: an MCP server that exposes home-lab checks as tools."""
import socket
import time

import httpx
from mcp.server.mcpserver import MCPServer

mcp = MCPServer("lab-tools")


@mcp.tool()
def check_url(url: str) -> str:
    """Fetch a URL and report the HTTP status and response time."""
    start = time.monotonic()
    try:
        r = httpx.get(url, timeout=5, follow_redirects=True)
        return f"HTTP {r.status_code} in {(time.monotonic() - start) * 1000:.0f} ms"
    except httpx.HTTPError as err:
        return f"failed: {err!r}"


@mcp.tool()
def check_port(host: str, port: int) -> str:
    """Test whether a TCP port on a host accepts connections."""
    try:
        with socket.create_connection((host, port), timeout=3):
            return f"{host}:{port} is open"
    except OSError as err:
        return f"{host}:{port} is closed or unreachable ({err})"


@mcp.tool()
def dns_lookup(name: str) -> str:
    """Resolve a host name to its IP addresses."""
    try:
        return ", ".join(sorted({ai[4][0] for ai in socket.getaddrinfo(name, None)}))
    except OSError as err:
        return f"lookup failed: {err}"


if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8701)
EOF

"""mcp-agent: an agent that gets its tools from the gateway's MCP endpoint.

The agent has no tools of its own. It asks LiteLLM which MCP tools its key may
use, hands them to the model, and runs the model's tool calls through LiteLLM.
"""
import asyncio
import json
import os
import sys

import httpx2
from mcp import Client
from mcp.client.streamable_http import streamable_http_client
from openai import OpenAI

GW, KEY = os.environ["GW"], os.environ["AGENT_KEY"]
llm = OpenAI(base_url=GW + "/v1", api_key=KEY)
SYSTEM = "You are a home-lab operations assistant. Use the tools to check facts. Answer briefly."


async def call_tool(mcp: Client, name: str, arguments: str) -> str:
    """Run one tool through the gateway. Mistakes go back to the model as text, so it can retry."""
    try:
        result = await mcp.call_tool(name, json.loads(arguments or "{}"))
    except Exception as err:                    # bad JSON from the model, or the gateway refused the call
        return f"error: {err}"
    return "\n".join(c.text for c in result.content if c.type == "text")


async def main(question: str) -> None:
    http = httpx2.AsyncClient(headers={"Authorization": f"Bearer {KEY}"}, timeout=60)
    async with Client(streamable_http_client(GW + "/mcp/", http_client=http)) as mcp:
        tools = (await mcp.list_tools()).tools
        print("tools from the gateway:", [t.name for t in tools], file=sys.stderr)
        specs = [{"type": "function", "function": {
            "name": t.name, "description": t.description or "", "parameters": t.input_schema}} for t in tools]

        messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}]
        for _ in range(8):

            if not msg.tool_calls:
                print(msg.content)
                return
            messages.append(msg.model_dump(exclude_none=True))
            for call in msg.tool_calls:
                text = await call_tool(mcp, call.function.name, call.function.arguments)
                print(f"  [mcp] {call.function.name}({call.function.arguments}) -> {text}", file=sys.stderr)
                messages.append({"role": "tool", "tool_call_id": call.id, "content": text})
        print("Stopped: too many steps.")


if __name__ == "__main__":
    asyncio.run(main(" ".join(sys.argv[1:]) or "What IP does rocky-linux resolve to, and is port 4000 open on 192.168.1.104?"))

"""coordinator: an agent whose only tool is "ask another agent" through the gateway."""
import json
import os
import sys
import uuid

import httpx
from openai import OpenAI

GW, KEY = os.environ["GW"], os.environ["AGENT_KEY"]
llm = OpenAI(base_url=GW + "/v1", api_key=KEY)
auth = {"Authorization": f"Bearer {KEY}"}


def list_agents() -> dict:
    """Ask the gateway which agents this key can see: {name: description}."""
    r = httpx.get(f"{GW}/v1/agents", headers=auth, timeout=30)
    r.raise_for_status()
    return {a["agent_name"]: a["agent_card_params"].get("description", "") for a in r.json()}


def ask_agent(agent: str, message: str) -> str:
    """Send one A2A message to an agent through the gateway and return its reply text."""
    body = {"jsonrpc": "2.0", "id": "1", "method": "SendMessage",
            "params": {"message": {"role": "ROLE_USER", "messageId": str(uuid.uuid4()),
                                   "parts": [{"text": message}]}}}
    try:
        r = httpx.post(f"{GW}/a2a/{agent}", json=body, headers={**auth, "A2A-Version": "1.0"}, timeout=300)
        data = r.json()
    except (httpx.HTTPError, ValueError) as err:    # too slow, unreachable, or a reply that isn't JSON
        return f"error from {agent}: {err!r}"
    if "error" in data:
        return f"error from {agent}: {data['error']}"
    try:
        task = data["result"]["task"]
        return "\n".join(p.get("text", "") for p in task["status"]["message"]["parts"])
    except (KeyError, TypeError):
        return f"error from {agent}: unexpected reply {str(data)[:300]}"


def main(goal: str) -> None:
    agents = list_agents()
    print("agents on the gateway:", list(agents), file=sys.stderr)
    if not agents:
        sys.exit("This key isn't allowed to use any agents.")
    roster = "\n".join(f"- {name}: {desc}" for name, desc in agents.items())
    tools = [{"type": "function", "function": {
        "name": "ask_agent", "description": "Delegate a task to one of the available agents.",
        "parameters": {"type": "object", "required": ["agent", "message"], "properties": {
            "agent": {"type": "string", "enum": list(agents)},
            "message": {"type": "string", "description": "A complete, self-contained request."}}}}}]
    messages = [
        {"role": "system", "content": "You are a coordinator. You cannot check anything yourself. "
                                      "Break the goal into steps and delegate each step to the best agent:\n" + roster},
        {"role": "user", "content": goal}]
    for _ in range(8):
        msg = llm.chat.completions.create(model="qwen3.8-27b", messages=messages, tools=tools).choices[0].message
        if not msg.tool_calls:
            print(msg.content)
            return
        messages.append(msg.model_dump(exclude_none=True))
        for call in msg.tool_calls:
            try:
                args = json.loads(call.function.arguments or "{}")
                agent, message = args["agent"], args["message"]
            except (ValueError, KeyError, TypeError) as err:    # arguments that don't fit: tell the model
                answer = f"error: ask_agent needs JSON with agent and message ({err!r})"
                print(f"  !! {answer}", file=sys.stderr)
            else:
                print(f"  -> {agent}: {message}", file=sys.stderr)
                answer = ask_agent(agent, message)
                print(f"  <- {agent}: {answer[:200]}", file=sys.stderr)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": answer})
    print("Stopped: too many steps.")


if __name__ == "__main__":
    main(" ".join(sys.argv[1:]) or "Check whether the gateway (http://192.168.1.104:4000/health/liveliness) "
                                    "and SSH on 192.168.1.104 are up, then have the results written up as a status update.")
EOF
